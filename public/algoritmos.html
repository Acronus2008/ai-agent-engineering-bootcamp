Approximate Nearest Neighbor (HNSW) Días 01-02 · RAG
Uso
Encontrar los k documentos más similares semánticamente a una query, dentro de un índice de embeddings.
Cuándo
Cualquier RAG a escala real — miles a millones de vectores. Con <10k documentos, brute-force alcanza.
Por qué
Comparar la query contra todos los vectores no escala. HNSW construye un grafo en capas que permite saltar directo a la vecindad correcta.
Qué sentido tiene
Sacrifica exactitud perfecta (es aproximado) por velocidad — en RAG, el top-5 "casi perfecto" en 10ms vale más que el top-5 exacto en 2s.
Brute-force: O(n·d) por query HNSW: ~O(log n) por query (aproximado) Espacio HNSW: O(n·M)
similarity_search.pypython
# Brute-force — correcto, pero O(n·d). Sirve como baseline / n pequeño.
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def brute_force_top_k(query: np.ndarray, vectors: list[np.ndarray], k: int = 5):
    scored = [(cosine_similarity(query, v), i) for i, v in enumerate(vectors)]
    scored.sort(reverse=True)
    return scored[:k]

# En producción no reimplementas HNSW a mano — usas una librería
# (faiss, hnswlib, o el vector store gestionado). Lo que sí decides
# es el trade-off: ef_search más alto = más recall, más latencia.
import hnswlib

index = hnswlib.Index(space="cosine", dim=1536)
index.init_index(max_elements=1_000_000, ef_construction=200, M=16)
index.add_items(vectors, ids)
index.set_ef(64)  # ef_search: sube esto si el recall no alcanza
labels, distances = index.knn_query(query, k=5)
Token Bucket Día 05 · Reliability
Uso
Limitar el throughput hacia el proveedor del LLM o hacia una tool downstream.
Cuándo
Cualquier tráfico saliente que pueda dispararse en loop (por un bug, por prompt injection, o simplemente por picos legítimos).
Por qué (vs. sliding window)
Permite ráfagas cortas controladas sin rechazar tráfico legítimo — más flexible que un contador fijo por ventana.
Qué sentido tiene
El "bucket" se rellena a tasa constante; cada request consume un token. Sin tokens, esperas o rechazas — el mecanismo es la analogía completa.
Tiempo: O(1) por request Espacio: O(1) por cliente
token_bucket.pypython
import time

class TokenBucket:
    def __init__(self, capacity: int, refill_rate_per_s: float):
        self.capacity = capacity
        self.tokens = capacity
        self.refill_rate = refill_rate_per_s
        self.last_check = time.monotonic()

    def allow(self) -> bool:
        now = time.monotonic()
        elapsed = now - self.last_check
        self.last_check = now
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)

        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False  # caller decide: rechazar, encolar, o degradar
Exponential Backoff + Jitter Día 05 · Reliability
Uso
Reintentar una llamada fallida sin generar retry storms sobre un sistema ya degradado.
Cuándo
Cualquier fallo transitorio (timeout, 503) — nunca para errores que no van a cambiar con un retry (ej. 400 de validación).
Por qué
El backoff exponencial da tiempo al sistema para recuperarse; el jitter evita que todos los clientes reintenten en el mismo instante (thundering herd).
Qué sentido tiene
Combinado con un circuit breaker (Closed → Open → Half-Open), evita seguir insistiendo cuando ya está claro que el sistema está caído.
Tiempo: O(1) por intento Intentos acotados: O(log(delay_max))
backoff.pypython
import random, time

def backoff_delay(attempt: int, base=0.5, cap=20.0) -> float:
    exp = min(cap, base * (2 ** attempt))
    return random.uniform(0, exp)  # "full jitter" — evita sincronización entre clientes

def call_with_backoff(fn, max_attempts=4):
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts - 1:
                raise
            time.sleep(backoff_delay(attempt))
Hashing determinístico (idempotency keys) Días 05, 07 · Reliability / Distributed Systems
Uso
Generar una clave estable que identifica "esta operación específica", para detectar duplicados sin coordinación central.
Cuándo
Toda escritura que pueda reintentarse — pagos, creación de tickets, cualquier acción de un Saga.
Por qué
Un hash de los parámetros relevantes (o un UUID generado una sola vez al iniciar el flujo) da la misma key ante el mismo intento, sin necesitar una base de datos externa para "acordar" la key.
Qué sentido tiene
A gran escala, guardar cada key vista puede ser costoso — ahí entra un Bloom filter: deduplicación aproximada con falsos positivos controlados y espacio sublineal.
Hash: O(1) Bloom filter: O(k) por insert/query (k = funciones hash) Espacio Bloom: O(m) sublineal vs. guardar cada key
idempotency.pypython
import hashlib, json

def idempotency_key(operation: str, params: dict) -> str:
    # sort_keys=True: mismo dict, mismo hash, sin importar el orden
    payload = json.dumps({"op": operation, "params": params}, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()

# Deduplicación aproximada a gran escala (millones de keys, memoria acotada)
from pybloom_live import BloomFilter

seen = BloomFilter(capacity=10_000_000, error_rate=0.001)

def is_probably_duplicate(key: str) -> bool:
    if key in seen:
        return True  # puede ser falso positivo — verificar contra la fuente real antes de rechazar
    seen.add(key)
    return False
Lamport Timestamps / Vector Clocks Día 07 · Distributed Systems
Uso
Determinar el orden causal de eventos generados por distintos servicios, sin depender de relojes de pared sincronizados.
Cuándo
Cuando el estado de un pedido se actualiza desde múltiples fuentes (ERP, agente, sistema de pagos) y necesitas reconciliar "qué pasó primero".
Por qué
Los relojes de máquinas distintas nunca están perfectamente sincronizados — usar wall-clock time para ordenar eventos produce inconsistencias silenciosas.
Qué sentido tiene
Cada nodo mantiene un contador que incrementa en cada evento y se sincroniza (toma el máximo) al recibir un mensaje — el orden relativo queda determinado sin reloj compartido.
Tiempo: O(n) por evento (n = número de nodos, para vector clocks) Lamport simple: O(1) por evento
lamport_clock.pypython
class LamportClock:
    def __init__(self):
        self.time = 0

    def tick(self) -> int:
        self.time += 1  # evento local
        return self.time

    def merge(self, received_time: int) -> int:
        # al recibir un mensaje, el reloj "salta" al máximo + 1
        self.time = max(self.time, received_time) + 1
        return self.time
Optimistic Locking (Compare-and-Swap) Día 07 · Distributed Systems
Uso
Evitar que dos ejecuciones concurrentes (ej. chat + voz del mismo usuario) pisen el mismo recurso al mismo tiempo.
Cuándo
Acciones críticas sobre un recurso compartido, cuando los conflictos son poco frecuentes (si son frecuentes, un lock pesimista/distribuido como Redlock rinde mejor).
Por qué
No bloquea nada por adelantado — lee la versión actual, escribe solo si nadie la cambió mientras tanto. Más barato que un lock distribuido real cuando la contención es baja.
Qué sentido tiene
Es la misma idea que un ETag HTTP o un WHERE version = ? en SQL — "solo actualiza si nadie más lo tocó desde que lo leí".
Tiempo: O(1) por intento Reintentos ante conflicto: acotados, igual que backoff
optimistic_lock.pypython
def update_order_status(order_id: str, new_status: str) -> bool:
    order = db.get(order_id)
    result = db.update(
        order_id,
        {"status": new_status, "version": order.version + 1},
        # condición: solo escribe si la versión no cambió desde la lectura
        condition="version = :expected_version",
        expected_version=order.version,
    )
    return result.success  # False → alguien más ganó la carrera, reintenta con datos frescos
Consistent Hashing Día 08 · Cloud Architecture
Uso
Distribuir sesiones o datos entre nodos (particiones de DynamoDB, instancias del Agent Runtime detrás de un load balancer).
Cuándo
Escalar horizontalmente añadiendo o quitando nodos, sin provocar un resharding masivo cada vez.
Por qué (vs. hash % n)
Con hash(key) % n, cambiar n remapea casi todas las keys. Con un anillo consistente, solo se remapean ~K/n claves al agregar/quitar un nodo.
Qué sentido tiene
Nodos y keys se ubican en el mismo anillo de hash; cada key pertenece al primer nodo en sentido horario. Los "virtual nodes" evitan que un nodo reciba una porción desproporcionada.
Lookup: O(log n) con anillo ordenado (bisect) Espacio: O(v) con v = virtual nodes
consistent_hash.pypython
import bisect, hashlib

class ConsistentHashRing:
    def __init__(self, nodes: list[str], virtual_nodes: int = 100):
        self.ring: dict[int, str] = {}
        self.sorted_keys: list[int] = []
        for node in nodes:
            for i in range(virtual_nodes):
                h = self._hash(f"{node}#{i}")
                self.ring[h] = node
        self.sorted_keys = sorted(self.ring)

    def _hash(self, key: str) -> int:
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_node(self, key: str) -> str:
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[idx]]
LRU Cache Transversal · Reliability / Cloud
Uso
Cachear resultados de tool calls costosas o embeddings ya calculados para no recomputarlos.
Cuándo
Hay reuso real de queries/resultados y el costo de recomputar (latencia o $/token) es alto.
Por qué
Evict la entrada usada menos recientemente asume que "lo usado hace poco se va a volver a usar pronto" — cierto para la mayoría de patrones de tráfico de agentes.
Qué sentido tiene
Un hashmap para lookup O(1) + una lista doblemente enlazada para saber qué es "más antiguo" — mover al frente en cada acceso.
Get/Put: O(1) Espacio: O(capacidad)
lru_cache.pypython
from functools import lru_cache

@lru_cache(maxsize=2048)
def embed_text(text: str) -> tuple[float, ...]:
    return tuple(embedding_model.encode(text))  # tuple: hasheable, cacheable

# Equivalente explícito, útil cuando necesitas TTL o métricas de hit-rate:
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.data: OrderedDict = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return None
        self.data.move_to_end(key)  # marca como "recién usado"
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)  # descarta el menos usado recientemente
Reservoir Sampling Día 05 · Observability
Uso
Samplear un subconjunto representativo de conversaciones para revisión humana o LLM-as-judge, sin guardar el 100% del tráfico.
Cuándo
Volumen alto donde persistir/revisar cada trace es demasiado caro, pero necesitas una muestra estadísticamente válida.
Por qué
No sabes cuántos elementos vas a ver en total (es un stream) — reservoir sampling garantiza que cada elemento tiene la misma probabilidad de terminar en la muestra, sin conocer n de antemano.
Qué sentido tiene
A medida que llegan más elementos, cada uno nuevo compite por un lugar en el "reservorio" con probabilidad k/i — matemáticamente da una muestra uniforme sin dos pasadas.
Tiempo: O(1) por elemento Espacio: O(k) con k = tamaño de la muestra
reservoir_sampling.pypython
import random

class ReservoirSampler:
    def __init__(self, k: int):
        self.k = k
        self.reservoir: list = []
        self.count = 0

    def add(self, item):
        self.count += 1
        if len(self.reservoir) < self.k:
            self.reservoir.append(item)
        else:
            j = random.randint(0, self.count - 1)
            if j < self.k:
                self.reservoir[j] = item  # reemplaza con probabilidad k/count
