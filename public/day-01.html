Enterprise AI Fundamentals

Qué diferencia a un agente enterprise de un chatbot: los bloques que vas a reconocer en cada arquitectura que veas de aquí en adelante.

~90 min Prerrequisito: ninguno Conecta con: Día 02 — Arquitectura de Agents
Objetivo del día

Al terminar hoy deberías poder explicar, sin apoyo, los 12 conceptos base de un sistema de IA enterprise — y sobre todo, poder traducir cada uno a un concepto que ya conoces de backend, APIs o cloud. No es contenido nuevo: es vocabulario nuevo para patrones que ya operaste.

Contenido
01 · LLM

Un servicio de predicción de tokens, no un cerebro

Un LLM recibe texto (tokens) y predice, uno a la vez, el token más probable que sigue — condicionado por todo lo que está en su ventana de contexto. No "recuerda" nada entre llamadas: cada invocación es independiente.

Analogía backendEs una función stateless: predict(context) → next_token. El estado (historial de conversación) lo maneja el caller, exactamente como un servicio REST sin sesión donde el cliente reenvía el contexto en cada request.
02 · Prompting

El contrato de comportamiento

El system prompt define reglas, tono, límites y formato — es la configuración del servicio. El user prompt es el request puntual. Un mal system prompt es como un servicio mal configurado: funciona, pero de forma impredecible.

Analogía backendSystem prompt ≈ variables de entorno / config que determinan el comportamiento del servicio antes de que llegue tráfico real.
03 · Structured Outputs

Forzar el output a un contrato validable

En vez de confiar en que el modelo devuelva texto libre parseable, se le fuerza (vía schema/grammar) a devolver JSON que cumple una estructura específica.

Analogía backendEs un DTO con validación de schema en el borde del sistema — igual que validar un payload contra OpenAPI/JSON Schema antes de aceptarlo.
04 · Function / Tool Calling

El modelo propone, tu backend decide y ejecuta

El LLM nunca ejecuta código. Cuando "llama una tool", en realidad devuelve un JSON con {name, arguments}. Tu backend valida esos argumentos y decide si ejecutar la función real. Este es el punto de control más importante de toda la arquitectura.

Analogía backendComo un webhook que el modelo "dispara": el payload lo genera el LLM, pero quien lo recibe, valida y ejecuta es tu código — con las mismas reglas de autorización que aplicarías a cualquier llamada externa no confiable.
05 · Agents

Un loop: pensar → actuar → observar → repetir

Un agente es un LLM dentro de un bucle de control: decide una acción (responder o llamar una tool), la ejecuta (o la ejecuta el sistema), observa el resultado, y decide el siguiente paso — hasta llegar a una respuesta final.

Analogía backendEs una máquina de estados / event loop con un paso de decisión no determinístico en cada iteración, en vez de transiciones fijas por código.
06 · Agent Orchestration

Coordinar pasos, tools y (a veces) otros agentes

Define cómo se secuencian las acciones: ¿un solo agente con muchas tools, o varios agentes especializados que se delegan trabajo entre sí? Determina también routing, reintentos y cuándo pedir intervención humana.

Analogía backendEs tu capa de orquestación de workflows (piensa Step Functions o un saga orchestrator), salvo que el "siguiente paso" lo decide el modelo, no un grafo fijo.
07 · RAG

Consultar el conocimiento en vez de entrenarlo

Retrieval-Augmented Generation: en el momento de responder, se buscan los documentos relevantes y se inyectan en el prompt. El modelo no "sabe" tu data privada — la consulta en tiempo real, igual que una app consulta su base de datos.

Analogía backendRAG es un read antes de responder — como resolver una vista con un join/lookup en vez de hardcodear el dato en el código. Fine-tuning, en cambio, sería "hornear" el dato en el modelo — caro y difícil de mantener actualizado.
08 · Embeddings & Vector DBs

Buscar por significado, no por coincidencia exacta

Un embedding convierte texto en un vector numérico donde la distancia refleja similitud semántica. Un vector DB es un índice optimizado para búsqueda por vecino más cercano sobre esos vectores.

Analogía backendComo un índice invertido de un motor de búsqueda full-text, pero en vez de matchear tokens exactos, matchea "cercanía de significado" en un espacio de alta dimensión.
09 · Context Window

El presupuesto de memoria de cada request

Todo compite por el mismo espacio limitado: system prompt, historial, documentos recuperados por RAG y resultados de tools. Se mide en tokens y tiene techo — cuando se llena, algo se trunca o descarta.

Analogía backendEs el heap/memory limit de un proceso por request: si no gestionas qué entra, tienes el equivalente a un OOM — salvo que aquí el "crash" es degradación silenciosa de calidad, no una excepción.
10 · Memory

Qué persiste, dónde y por cuánto tiempo

Short-term: el historial de la conversación actual, vive en el contexto. Long-term: hechos, preferencias o resúmenes que persisten entre sesiones, normalmente en una base de datos externa al modelo.

Analogía backendShort-term memory ≈ estado de sesión en memoria. Long-term memory ≈ persistencia en una tabla/store, con las mismas preguntas de siempre: qué se guarda, con qué TTL, y quién tiene acceso.
11 · Hallucinations

El modo de falla más peligroso: falla con confianza

El modelo genera texto plausible pero falso — no hay excepción, no hay stack trace. En un contexto enterprise (saldo de cuenta, estado de un pedido), esto es inaceptable sin mitigación.

Analogía backendEs el equivalente a un servicio que devuelve 200 OK con datos incorrectos en vez de fallar explícitamente. Por eso todo dato factual crítico debe venir de una tool/RAG verificable, nunca de la "memoria" del modelo.
12 · Guardrails

Middleware de validación alrededor del modelo

Capas de control sobre input y output: filtros de contenido, validación de schema, un segundo modelo como "juez", límites de qué tools se pueden llamar y con qué permisos.

Analogía backendEs tu capa de middleware/API gateway: sanitiza el input, valida el output, aplica rate limiting y políticas — el modelo nunca es el único punto de control.

Ejemplo de implementación

Tool schema + validación, en código

El esqueleto del ejercicio de abajo: el schema que ve el modelo, y la validación que corre antes de tocar el ERP real — nunca al revés.

order_agent.pypython
# El schema que el modelo ve — define la forma, no la confianza
GET_ORDER_STATUS_SCHEMA = {
    "name": "get_order_status",
    "description": "Consulta el estado de un pedido por su ID",
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "pattern": "^[0-9a-fA-F-]{36}$"}
        },
        "required": ["order_id"],
    },
}

def execute_tool_call(name: str, args: dict) -> dict:
    # 1. Validar ANTES de tocar el sistema real — nunca confiar
    #    solo en el schema que "vio" el modelo.
    if name == "get_order_status":
        order_id = args.get("order_id", "")
        if not UUID_PATTERN.match(order_id):
            # Error estructurado, no una excepción cruda —
            # el agente lo recibe como observación y puede reaccionar.
            return {"error": "invalid_order_id", "detail": "expected UUID format"}

        try:
            status = erp_client.get_status(order_id)  # única fuente de verdad
            return {"status": status}
        except ERPTimeoutError:
            return {"error": "upstream_timeout"}

    return {"error": "unknown_tool"}

Nota lo que no hace este código: nunca deja que el agente afirme un estado sin pasar por erp_client.get_status — es la barrera anti-alucinación del Día 01 hecha código.

Ejercicio práctico

Caso: agente de estado de pedidos

Una empresa quiere un agente que responda "¿dónde está mi pedido?" consultando el ERP interno. Diseña el flujo de function calling respondiendo:

  1. ¿Qué forma tiene el schema de la tool get_order_status? ¿Qué parámetros son obligatorios?
  2. El LLM llama la tool con order_id: "ABC" pero el sistema real espera un UUID numérico. ¿Qué pasa?
  3. ¿Cómo evitas que el modelo alucine un order_id o invente un estado de envío si la tool falla?
Ver enfoque sugerido

1. Schema: {order_id: string, required, pattern: UUID} — describe el schema en la definición de la tool para que el modelo sepa el formato esperado, pero nunca confíes solo en eso.

2. Validación: tu backend valida el order_id antes de tocar el ERP. Si no matchea el patrón, devuelves un error estructurado a la tool (no una excepción cruda) — el agente lo recibe como observación y puede pedir aclaración al usuario o reintentar con el formato correcto.

3. Anti-alucinación: el prompt del agente debe dejar explícito que solo puede afirmar un estado de pedido si viene de un resultado de tool exitoso — nunca "recordado" o "inferido". Si la tool falla, la respuesta correcta es admitir que no se pudo consultar, no inventar un estado plausible.
