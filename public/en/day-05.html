05

Production AI & Reliability

Retries, circuit breakers, and idempotency you already master from classic backend. Today: apply them to an agent's loop, and the new layer — evals, cost per token, and prompt versioning.

~100 min Prerequisite: Day 04 Connects to: Day 06 — System Design
Today's objective

Close Week 1 with the question that separates a demo from a real solution: what happens when something fails? — a tool call, the LLM, the network — and how you'd know before an angry customer tells you.

Content
Classic reliability, applied to the agent's loop
Retries & Timeouts

Every tool call and every LLM call needs both

Without a timeout, an agent's loop can hang indefinitely mid-conversation. Retries must be bounded (backoff, max attempts) — never let the agent retry indefinitely within its own reasoning.

Circuit Breakers

Fail fast when a dependency is down

If a tool fails repeatedly, the circuit breaker cuts calls and forces an immediate fallback — it keeps the agent from continuing to "try" while the user waits.

Idempotency

Critical when the one retrying can be the agent OR the user

A timeout followed by a retry, or a user repeating "do it again," can trigger the same action twice. Every state-modifying tool needs an idempotency key.

Fallbacks

A degraded response beats hanging

If a tool is unavailable: "I can't check that right now, let me connect you with someone" — never let the agent invent the missing data.

Rate Limiting

Protects the LLM provider and downstream systems

An agent stuck in a loop (from a bug or an injection) can generate explosive traffic toward tools or the model provider — it needs limits like any automated client.

Queues & DLQ

For the asynchronous actions an agent triggers

A fulfillment event that fails after its retries shouldn't be silently lost — it goes to a dead-letter queue for investigation, same as any async pipeline.

Observability, Tracing, Metrics, Logging

A single trace spanning LLM calls + tool calls + orchestration

The difference from classic backend: you need to see the full reasoning chain of a request — what the model decided, which tool it called, with what result, in what order — as a single distributed trace, not scattered calls.

What's specific to AI in production
Model Fallback

What happens if the LLM provider is down

Pluggable architecture: if the primary model fails or degrades, it falls back to a secondary model (another provider or a simpler one) — with the explicit expectation that quality may drop temporarily.

Token Usage & Cost

A runaway loop is also a cost incident

Every session/request should have a token budget. Without a limit, a bug in the orchestration logic (or an injection) can trigger a loop that runs up cost without anyone noticing until the bill arrives.

Latency

The LLM is almost always the slowest step in the pipeline

Response streaming, parallelizing independent tool calls where possible, and budgeting latency per step — just like you'd optimize any high-latency request.

Hallucination Monitoring

Not a test you pass once, a continuous metric

Production signals: rate of responses unsupported by retrieved documents, contradictions flagged by an evaluator model, negative user feedback — tracked over time, not just validated pre-launch.

Tool Failures

Must reach the agent as a structured observation, never swallowed

If a tool fails and the error is silently swallowed, the agent may hallucinate a result. A structured error gives the agent the information to decide: retry, use a fallback, or escalate.

Prompt / Version Management

Prompts are code: versioned, tested, with rollback

A prompt change is a production behavior change — same rigor as a deploy: canary, evaluation before 100% rollout, ability to revert.

Agent Evaluation

Offline (golden set) + online (sampling real conversations)

A fixed test-case set catches regressions before deploy. Continuous sampling of real conversations (human review or LLM-as-judge) catches what the golden set didn't anticipate.

Implementation diagram

Retry + idempotency in action

The same idempotency_key travels on both attempts — that's what turns a timeout plus a retry into "one single operation," not two.

Implementation example

Idempotent wrapper with bounded retry

The key is generated once, at the start of the flow — never inside the retry loop.

reliable_tool_call.pypython
import time, uuid

def call_with_retry(fn, *, max_attempts=2, timeout_s=5, backoff_s=1):
    idempotency_key = str(uuid.uuid4())  # generated ONCE, outside the loop

    for attempt in range(1, max_attempts + 1):
        if circuit_breaker.is_open(fn.__name__):
            return fallback_response()  # fail fast, no more attempts

        try:
            result = fn(idempotency_key=idempotency_key, timeout=timeout_s)
            circuit_breaker.record_success(fn.__name__)
            return result
        except TimeoutError:
            circuit_breaker.record_failure(fn.__name__)
            if attempt == max_attempts:
                return fallback_response()
            time.sleep(backoff_s * attempt)  # short, bounded backoff

def fallback_response() -> dict:
    # Honest with the user, never invents a result
    return {"status": "pending_verification", "message": "We're confirming your ticket."}

The circuit_breaker is just a counter with a threshold and a flag — you don't need a library to get started, just the discipline of never retrying without a limit.

Practical exercise

Case: the "create ticket" tool intermittently fails with a timeout

One out of every twenty calls to create_ticket times out at 5s, but the ticket is sometimes actually created on the legacy system's side (the timeout is on the response, not the operation).

  1. How do you design the idempotency key for this tool?
  2. What retry policy would you apply, and why?
  3. What does the user see in the meantime, and what stays in the trace to debug it later?
See suggested approach

1. An idempotency key generated by the agent when it starts the operation (not by the legacy system), sent on every attempt — the ticket backend uses it to detect "I already processed this" and return the same result instead of creating a duplicate.

2. A single retry with short backoff, and if it fails again, stop — don't keep retrying indefinitely — move to a fallback (tell the user it's being verified) instead of letting the agent "decide" to retry on its own within its reasoning.

3. The user sees an honest message ("I'm confirming whether the ticket was created"), never an unverified claim. The trace must record the idempotency key, each attempt, its timeout, and the final verification result — so you can reconstruct exactly what happened if the customer reports a duplicate ticket.
