Voice & Multichannel Agents

Expanded from Day 10 (enterprise voice agent) — full detail here.

Perceived latency

A 2s silence in voice feels like a failure; the same delay in chat goes unnoticed. Budget latency per pipeline stage STT→LLM→TTS.

Interruptions (barge-in)

The user can speak while the agent is responding — the system must be able to cut off TTS and process the new input without losing context.

Conversation state

With no visual UI, the state of "where we are in the conversation" lives entirely in the backend — the user can't "scroll up" to remember.

Human handoff / call transfer

The human who receives the call needs the full context (transcript + detected intent) so the customer doesn't have to repeat everything.

Voice authentication

With no UI, you fall back on verbal PIN, two-factor verification, or voice biometrics — weaker than visual authentication, requires explicit design.

Self-check: can I explain why latency matters more in voice than in chat, without hesitating?

Software Engineering Deep Dive

This isn't studying Java/Spring from scratch — it's being able to defend decisions and go from architecture down to implementation when asked.

APIs & Microservices

You can design a tool's contract the same way you would for any microservice: versioning, input validation, explicit error handling.

Concurrency & Async

The Agent Runtime likely handles multiple tool calls in parallel when they're independent — be able to explain how you'd avoid race conditions there.

Resilience Patterns

Retry, timeout, circuit breaker — you already saw these applied to agents on Day 05. Be able to implement them in code, not just describe them.

Clean Architecture & SOLID

If asked to design a component (e.g. a tool's adapter), demonstrate layer separation: business logic shouldn't depend on the LLM SDK.

Testing

Think about how you'd test a tool with external dependencies (mocks) and how you'd test the agent's own behavior (evals, Day 05).

Self-check: could I implement in code, not just explain, one of the tools I designed this week?

Track 🟠 Medium

Data Architecture

Leverage your existing Data Engineering experience — the new question is how it connects to RAG.

OLTP vs OLAP

Transactional systems (OLTP) feed the Data Platform; the Knowledge Layer that RAG consumes usually derives from a more analytical/curated layer (OLAP-like), not from the raw transactional table.

CDC & Streaming

Change Data Capture keeps the Knowledge Layer updated near real-time, instead of reindexing a full batch every time.

Data Governance & Quality

If the source data is mislabeled or stale, RAG inherits it directly — the agent's quality starts with the data pipeline's quality.

Key track question: how do we keep the knowledge the agent uses current and trustworthy?

Track 🟠 Medium

DevOps / CI-CD

How an AI solution goes from code to production in a controlled way — no different from any other system, with nuances.

Docker & Kubernetes

The Agent Runtime is packaged and deployed just like any other service — nothing AI-specific here, beyond managing the LLM provider's credentials like any secret.

Blue/Green & Canary

Especially relevant for prompt or model changes (Day 05) — a canary rollout lets you measure quality before exposing the change to 100% of traffic.

Feature Flags

Useful for turning agent capabilities on/off (e.g. a risky new tool) without needing a new deploy.

Rollback Strategies

If a prompt change degrades quality, you need to be able to revert as fast as you'd revert a code bug — prompt versioning (Day 05) is what makes that possible.

Self-check: how would I roll back a prompt change that degraded quality in production?
