AI Agent Architecture

The same 12 concepts from yesterday, now as boxes in a diagram: where each component lives and how it connects to the company's systems.

~90 min Prerequisite: Day 01 Connects to: Day 03 — Enterprise Integration
Today's objective

Go from "I know what RAG is" to "I know where to draw the RAG box in an architecture diagram, and what's on each side." By the end you should be able to draw an enterprise agent's base diagram from memory.

Base diagram
Content
Agent Runtime

The loop that orchestrates everything else

It's the process that receives the user's message, assembles context (system prompt + memory + RAG results), calls the LLM, interprets its decision, executes tools if needed, and repeats until it has a final answer.

Backend analogyIt's your application server orchestrating a business transaction that touches several systems — except the "controller" for each step is a model decision, not a fixed code branch.
Tools

The only door to real systems

Every business capability (query CRM, create a ticket, update an order) is exposed as a tool with an input/output schema and its own authorization scope. The agent sees a list of available tools — never credentials or direct access.

Backend analogyIt's exactly a Backend-for-Frontend: it wraps legacy/internal systems behind a clean contract, with per-endpoint authorization.
Memory (architecturally)

Two tiers, two distinct physical places

Short-term lives in the active session's context (cache/process). Long-term lives in a persistent store (relational DB, document store, or vector store) and is explicitly retrieved when a new session starts.

Backend analogyShort-term ≈ session cache (Redis). Long-term ≈ a profile/history table you query when authenticating the user.
RAG (architecturally)

Two separate pipelines: ingestion and query

Ingestion (offline/batch): documents → chunking → embeddings → vector store. Query (online, per request): question → embedding → similarity search → injection into the prompt.

Backend analogyIngestion ≈ your ETL pipeline that feeds a search index. Query ≈ the hot-path query against that index on every request — the same read/write separation you already know.
State

What's currently running, and at which step

Includes: conversation history, which tools were called and with what result, and whether there's an action pending human approval. It's what you need to persist to be able to pause and resume a long flow.

Backend analogyIt's the execution history of a workflow engine (think Step Functions): each step, its input, its output, and the pointer to "where we are now."
Agent Orchestration

Single-agent vs multi-agent

A single agent with several tools is simpler to operate and debug. A multi-agent setup (e.g., planner + specialists) makes sense when you need to separate knowledge domains, apply different security limits per tool-set, or achieve real parallelism between subtasks.

CriterionSingle-agentMulti-agent
Operational complexityLowHigh (routing, handoffs, distributed debugging)
Security isolationSingle tool scopeDistinct scopes per agent/domain
When it fitsBounded domain, few toolsHeterogeneous domains, need for specialization
Typical riskOverloaded promptFragile coordination between agents
Implementation example

The Agent Runtime loop, in code

The real skeleton behind the diagram's boxes: build context, call the model, execute tools, repeat until there's a final response.

agent_runtime.pypython
class AgentRuntime:
    def __init__(self, llm_client, tools: dict, memory_store, rag_index):
        self.llm = llm_client
        self.tools = tools            # {name: callable function}
        self.memory = memory_store    # short-term + long-term
        self.rag = rag_index

    def handle_message(self, session_id: str, user_message: str) -> str:
        history = self.memory.get_conversation(session_id)
        relevant_docs = self.rag.search(user_message, top_k=3)
        context = build_context(history, relevant_docs)

        while True:  # the loop: think → act → observe
            response = self.llm.call(context, tools=self.tools_schema())

            if response.stop_reason == "tool_use":
                tool_fn = self.tools.get(response.tool_name)
                result = tool_fn(**response.tool_args)  # validated inside tool_fn
                context.append_tool_result(response.tool_name, result)
                continue  # call the LLM again with the result

            # stop_reason == "end_turn" → final response
            self.memory.save_turn(session_id, user_message, response.text)
            return response.text

The while True is the real mechanism behind "the agent decides the next step" — there's nothing more mystical than a loop with a clear exit condition.

Practical exercise

Case: customer support agent

It must: (a) answer FAQs with RAG, (b) look up order status in the ERP, (c) escalate to a human when unsure. Draw the diagram's boxes for this case and answer:

  1. Does this case justify multi-agent, or is a single agent with 2 tools + RAG enough? Why?
  2. Where's the trust boundary — what can the agent decide alone, and what needs human approval?
  3. What happens to the state if the conversation drops mid-way through an ERP lookup?
See suggested approach

1. A single agent is enough: it's two related domains (support) and few tools. Multi-agent here would be over-engineering — it adds coordination without real benefit.

2. The agent can answer FAQs and check status freely (they're read-only operations). Any action that modifies order state (cancel, refund) should require human handoff or an explicit approval workflow — not direct autonomy.

3. The state must persist the tool call's partial result (or its absence) so that, on resume, the agent knows whether it already queried the ERP or needs to retry — avoiding a duplicate lookup or losing conversation context.

Related interview questions
  • When would you justify splitting an agent into several specialized agents?
  • Where does an agent's state live, and why does that matter for scaling to multiple concurrent users?
  • How would you design a tool's limits so the agent can't do more than it should?
  • What breaks if you put all the business logic in the prompt instead of in tools?
  • What does RAG's ingestion pipeline look like compared to the query pipeline?
