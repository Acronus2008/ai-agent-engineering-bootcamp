Cloud Architecture (AWS)

You already know the services. Today's goal is to defend the choice, not list features — practicing the five comparisons that come up most in interviews.

~90 min Prerequisite: Day 07 Connects to: Day 09 — Composition Case
Today's objective

The goal isn't to memorize services — it's to justify decisions and trade-offs. Walk through the five comparisons applied to the same case: a support agent that needs to execute tools, orchestrate a multi-step flow, and store conversation state.

The five comparisons
Lambda vs ECS / EKS
LambdaIndividual tool execution: short-lived, stateless, unpredictable traffic. You pay per invocation, cold start is acceptable if the tool isn't latency-critical.
ECS / EKSThe Agent Runtime itself: a long-running process, holds connections (streaming to the user), needs guaranteed warm start and more control over resources.
API Gateway vs ALB
API GatewayThe agent's tool-call layer: per-route auth, throttling, request/schema validation per endpoint — fits many small, well-defined endpoints (one tool = one route).
ALBRouting to a smaller number of long-running services/containers, cheaper at high throughput, less "intelligence" per request.
SQS vs Kafka (MSK)
SQSPoint-to-point work distribution: a queue of "actions pending human approval," a single consumer processes each message once.
Kafka / MSKAn agent event ("conversation completed") that several independent systems need to consume (analytics, CRM sync, billing) — each consumer keeps its own offset.
Step Functions vs Kafka
Step FunctionsOrchestrate a defined sequence with built-in retry and error handling — the natural fit to implement the Day 07 Saga (refund: verify → charge → update → notify).
KafkaDecoupled reactions where no one needs to "own" the full sequence — each system reacts to the event at its own pace, without a central orchestrator.
DynamoDB vs RDS / PostgreSQL
DynamoDBConversation state: key-based access pattern (session_id), needs to scale with concurrent conversations, low-latency reads, little need for joins.
RDS / PostgreSQLRelational business data (orders, customers) where you need joins, strong consistency, and complex queries — not the place for chat history.
The rest of the stack, one line each
EventBridge

A schema-aware event bus, for routing agent events to multiple targets by rule — without building your own router.

S3

Where raw documents land before the Day 02 RAG ingestion pipeline chunks and embeds them.

Secrets Manager

Tools never have credentials in code or plain env vars — they fetch them at runtime, with automatic rotation.

CloudWatch (+ X-Ray)

The aggregation point for logs/metrics, and the AWS-native way to build the Day 05 distributed trace.

IAM

Every tool's Lambda has its own role with minimum permission — the concrete version of Day 04's least privilege.

Implementation example

Triggering the Saga from the Agent Runtime

The ECS Runtime doesn't run the Saga directly — it triggers a Step Functions execution and moves on with the conversation.

trigger_refund_saga.pypython
import boto3, json, uuid

sfn = boto3.client("stepfunctions")

def start_refund_saga(order_id: str, amount: float) -> str:
    execution_name = f"refund-{order_id}-{uuid.uuid4().hex[:8]}"

    response = sfn.start_execution(
        stateMachineArn=REFUND_SAGA_ARN,
        name=execution_name,        # Step Functions rejects duplicate names
        input=json.dumps({                  # → free idempotency at the execution level
            "order_id": order_id,
            "amount": amount,
            "idempotency_key": execution_name,
        }),
    )
    return response["executionArn"]  # the agent can poll its status later

The execution name does double duty: it identifies the run and acts as an idempotency key — Step Functions rejects a start_execution with a name already in use.

Practical exercise

Case: taking the support agent (Day 02) to AWS

Decide, with a one-sentence justification each:

  1. Where does the Agent Runtime live — Lambda or ECS?
  2. Where does the conversation state live?
  3. How do you implement the Day 07 "process refund" Saga with concrete AWS services?
See suggested approach

1. ECS (or similar), because the runtime needs to keep streaming the response to the user and make multiple LLM/tool calls within the same request — a Lambda cold start on every conversation turn would be a bad experience. The individual tools can still be Lambdas.

2. DynamoDB, indexed by session_id — low-latency key access, and it scales naturally with concurrent conversations without needing joins.

3. Step Functions orchestrates the 4 steps (verify → charge → update order in RDS → notify), with per-step retry configured and an explicit error branch to a "human review" SQS queue if the update step fails after the charge was already issued.

  • Why might DynamoDB be better than RDS for conversation state, and when would that flip?
