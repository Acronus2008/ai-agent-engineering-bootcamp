The case
Prompt

"A company wants to implement an AI agent that handles customers by voice, queries internal systems, executes operations, and transfers the conversation to a human when necessary."

⏱ 60 min to solve 🎙 Ideally: record yourself talking, not just writing 📋 Use the Day 06 16-step framework

Suggested approach
See the full solution (all 16 steps)
  1. 1. Clarify "What kind of operations does it execute — queries only, or also state-changing actions (e.g., canceling a service)? What voice channel — a traditional call center or WhatsApp/app?" We assume: inbound call center, queries + low-to-medium-risk actions, with high-impact refunds/changes escalating to a human.
  2. 2. Users End customers (calling in), human support agents (receive the handoff), supervisors (audit call quality).
  3. 3. Objectives Reduce wait time and cost per call, while keeping NPS steady and human escalation under 20% — a concrete KPI, not "use AI."
  4. 4. Functional Authenticate the caller, look up account/orders, execute simple actions (reschedule, update a field), transfer with context to a human.
  5. 5. Non-functional Perceived response latency <1.5s (critical in voice — long silences feel like a failure), high availability 24/7, traffic spikes during business hours.
  6. 6. Constraints Legacy CRM systems, call-recording regulation, the human support team already runs on an existing dialer.
  7. 7. High-level architecture Phone → STT → Agent Runtime → (Tools/RAG) → TTS → Phone, with handoff to a human via the existing dialer.
  8. 8. Agent architecture The Day 02 base diagram: Agent Runtime + LLM + Memory (call state) + RAG (FAQ/policies) + Tools (CRM, rescheduling system).
  9. 9. Integrations CRM via REST + OAuth2 (Day 03), state-changing actions with an idempotency key, call transfer via the telephony provider's API.
  10. 10. Data Call state in DynamoDB (Day 08), customer history via RAG over the knowledge base, never persist raw audio longer than strictly necessary for compliance.
  11. 11. Security Voice authentication is weaker than chat (no visual UI) — a verbal PIN or 2-factor verification before any sensitive action. Unrestricted read-only tools; write tools with minimum scope (Day 04).
  12. 12. Resilience If STT fails or there's excessive noise, fall back to "I didn't quite catch that, can you repeat?" before escalating. If the LLM is slow, a holding message avoids awkward silence (perceived as a failure in voice).
  13. 13. Observability A full per-call trace (Day 05): transcript, tool calls, the escalate-or-not decision, and timing at each stage of the STT→LLM→TTS pipeline.
  14. 14. Scalability The most likely bottleneck is the STT/TTS provider under traffic spikes — design with multiple providers or wait queues with time estimates, not a service outage.
  15. 15. Trade-offs A bigger model gives better answers but more latency — in voice, perceived latency outweighs "smarter but slow," so a faster model with tightly-scoped RAG is prioritized.
  16. 16. Rollout Pilot with a subset of low-risk call types (status queries), measure resolution rate and NPS before enabling state-changing actions.
Voice-specific considerations
What's different from a chat channelPerceived latency (a 2s silence feels like a failure, a 2s delay in chat doesn't), handling interruptions (barge-in: the user speaks while the agent is responding), and authentication without a visual UI. Implementation example

Handling barge-in, in code

The voice-specific case that doesn't exist in chat: canceling the audio currently playing the moment the user starts talking over it.

voice_session.pypython
class VoiceSession:
    def __init__(self, call_id: str):
        self.call_id = call_id
        self.tts_task: asyncio.Task | None = None

    async def on_audio_chunk(self, chunk: bytes):
        # If the agent is speaking and new user audio arrives,
        # it's barge-in: stop playback NOW, don't wait for it to finish.
        if self.tts_task and not self.tts_task.done():
            self.tts_task.cancel()
            await self.telephony.stop_playback(self.call_id)

        await self.stt_stream.feed(chunk)

    async def on_utterance_end(self, transcript: str):
        response_text = await self.agent_runtime.handle_message(self.call_id, transcript)
        self.tts_task = asyncio.create_task(self._speak(response_text))

    async def _speak(self, text: str):
        audio_stream = await self.tts.synthesize(text)
        await self.telephony.play(self.call_id, audio_stream)

Explicitly canceling tts_task is what keeps the agent from "talking over" the user — the most noticeable UX bug in poorly implemented voice agents.
