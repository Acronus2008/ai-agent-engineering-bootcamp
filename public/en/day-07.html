Distributed Systems

CAP, Saga, Outbox, idempotency — you already know all of this. Today: apply it to the question every FDE interviewer asks sooner or later.

~100 min Prerequisite: Day 06 Connects to: Day 08 — Cloud Architecture
Today's objective

Answer solidly: "what happens if an agent tries to execute the same operation twice?" — and do it covering idempotency, transactional limits, authorization, auditing, and retry strategy in a single structured answer.

Content
CAP Theorem

Applied to tool decisions, not just databases

During a partition, does the tool prioritize consistency (reject the request) or availability (respond with potentially stale data)? It depends on the cost of each error: a stale "order status" is tolerable; a stale "available balance" is not.

Eventual Consistency

Acceptable for most of an agent's reads

If the agent reads from a read replica or a RAG index that updates every X minutes, that's eventual consistency — perfectly valid for informational questions, not for decisions that move money or inventory.

Distributed Transactions & Saga

An agent action is almost never a single ACID transaction

"Process a refund" can touch: payment system, orders database, notification system — each with its own local transaction. The Saga pattern chains these steps with compensating actions: if step 3 fails, you undo (or compensate for) the effects of steps 1 and 2 that already executed.

Outbox Pattern

Reliably publishing an event alongside a state change

When a tool updates its database AND needs to emit an event (e.g., "refund processed" → notify the agent to inform the user), writing both in the same local transaction (an outbox table) and publishing the event afterward, asynchronously, avoids the case where the state changes but the event gets lost.

Ordering

The order of tool calls matters, and the model doesn't always guarantee it

If the agent must "check inventory" before "charging," that precondition must be validated inside the tool itself (reject the charge if there's no recorded prior verification) — never trust that the LLM will always respect the correct order.

Exactly-once vs At-least-once

Exactly-once doesn't exist at the network level — it's simulated with idempotency

Assume any tool call can arrive more than once (at-least-once, from retries). The "effectively-once" outcome is achieved by combining at-least-once delivery with an idempotent tool — not by chasing real exactly-once, which is practically impossible to guarantee end-to-end.

Distributed Locks

When two channels could trigger the same action at once

If the same user is interacting via chat and voice simultaneously, a lock on the operation's key (e.g., order_id) prevents both conversations from executing the same critical action in parallel.

Backpressure, Queues & Streams

A quick review with agent vocabulary

Backpressure = the system tells the orchestrator "slow down" instead of falling over. Queues = point-to-point work distribution (one task, one consumer). Streams (Kafka) = an ordered log, multiple independent consumers — useful when several systems need to react to the same agent event.

Implementation example

Saga orchestrator, in code

The general pattern: each step knows how to execute and, if applicable, how to compensate.

refund_saga.pypython
class SagaStep:
    def __init__(self, name, execute, compensate=None):
        self.name, self.execute, self.compensate = name, execute, compensate

def run_saga(steps: list[SagaStep], context: dict):
    completed = []
    for step in steps:
        try:
            context = step.execute(context)
            completed.append(step)
        except StepFailed as e:
            # Compensate in reverse order — but the payment (step 2) isn't
            # "reverted": its real compensation is to escalate, not undo.
            for done in reversed(completed):
                if done.compensate:
                    done.compensate(context)
            raise

refund_saga = [
    SagaStep("verify", verify_eligibility),
    SagaStep("charge", issue_refund, compensate=escalate_to_review),
    SagaStep("update_order", update_order_status),  # uses Outbox internally
    SagaStep("notify", notify_customer),
]

The charge compensation doesn't revert the payment — it calls escalate_to_review, which is what we discuss in the exercise below.

Practical exercise

Case: process a refund via an agent

Flow: (1) verify eligibility (read), (2) issue the refund with the payment provider (external write, can fail partially), (3) update the order status (internal write), (4) notify the customer.

  1. How do you structure this as a Saga? What's the compensating action if step 3 fails after step 2 already executed?
  2. Where would you use the Outbox pattern?
  3. What needs to be idempotent, and with what key?
See suggested approach

1. Each step is a local transaction with its own compensation. If step 3 (update order) fails after the refund was already issued (step 2), the compensation is NOT "revert the refund" (rarely possible or desirable) — it's retrying step 3 until it succeeds, or escalating to human review if it keeps failing, leaving the already-issued refund flagged as "pending reconciliation."

2. In step 3: when updating the order status in the same local transaction, you also write the "refund processed" event to an outbox table — a separate process reliably publishes it, triggering the customer notification (step 4) without coupling that notification to the database transaction.

3. The call to the payment provider (step 2) needs an idempotency key generated at the start of the flow (not on each retry) — that way, if the agent retries the whole flow due to a timeout, the payment provider recognizes it as the same operation and doesn't issue a second refund.
