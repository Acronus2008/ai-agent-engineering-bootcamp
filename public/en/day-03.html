03

Enterprise Integration

The agent lives surrounded by CRM, ERP, queues, and legacy APIs. Today is pure mapping: which protocol to use for which capability, and how to authorize every call.

~90 min Prerequisite: Day 02 Connects to: Day 04 — Security
Today's objective

You already know how to build APIs, consume events, and handle OAuth2 — that doesn't change. What changes is who decides when to call each integration: today it's an LLM, not a fixed code branch, so every integration needs a more explicit, more defensive contract.

Key principle
"The agent should not access critical systems directly; it must do so through tools and APIs with proper authorization and controls."
Content
REST

The default for exposing a tool

Synchronous request/response, predictable contract, easy to describe as a schema for the LLM. It's the simplest way to wrap a business capability as a tool.

GraphQL

Powerful for a human, ambiguous for the model

It solves over/under-fetching, but a full GraphQL schema is hard to bound as a tool definition (too many possible combinations). In practice: wrap the GraphQL behind a REST-like tool with predefined, parameterized queries.

Kafka / Event-driven

For actions that don't need an immediate response

If the agent's action triggers a downstream process (fulfillment, notifying another team) and doesn't need to wait for the result to continue the conversation, an event beats a synchronous call: it decouples the agent from that system's availability.

Webhooks

How the world wakes the agent up

When something happens outside the conversation turn (a payment confirms, a human approves a pending action), a webhook reactivates the agent to continue where it left off — key for human-in-the-loop flows.

Databases

Never a tool by itself

The agent shouldn't have a "run SQL query" type tool. It should always go through a service that validates, applies business rules, and leaves an audit trail — the same as you'd require in any system with external users.

CRM / ERP / SaaS / Legacy

Reality: a clean API is rare

You often need an adapter/anti-corruption layer between the legacy system and the tool you expose to the agent — it translates the old data model into a simple, stable contract.

OAuth2 / OIDC

Who authorizes what, on whose behalf

The agent acts on behalf of a user (delegated authorization) or with a scoped service account. The token a tool uses must carry the same scopes the user would have if performing the action manually — never more.

IAM

Least privilege, per tool

Every tool has its own minimum necessary scope. An "order lookup" tool shouldn't be able to "cancel order" — even if both touch the same system.

API Gateway

The chokepoint where control lives

Every one of the agent's tool calls passes through a central point of auth, rate limiting, and logging — it's also usually where a good chunk of the security guardrails live (Day 04).

Implementation example

The adapter wrapping the legacy SOAP system

The tool the agent sees is clean REST; the adapter absorbs all of SOAP's ugliness behind it.

ticket_adapter.pypython
from fastapi import FastAPI, HTTPException
import zeep  # SOAP client

app = FastAPI()
soap_client = zeep.Client("https://legacy.internal/tickets?wsdl")

# Clean REST contract — this is the only thing the agent knows as a tool
@app.post("/tickets")
def create_ticket(payload: TicketCreate, token: str = Depends(verify_oauth_scope)):
    if not token.has_scope("tickets:write"):
        raise HTTPException(403, "missing tickets:write scope")

    try:
        # Translates the simple REST model into the actual SOAP request
        soap_response = soap_client.service.CreateIncident(
            CustomerId=payload.customer_id,
            Description=payload.description,
            Priority=map_priority(payload.priority),
        )
    except zeep.exceptions.Fault as e:
        # Structured error — the agent sees it as an observation, not a crash
        raise HTTPException(502, {"error": "legacy_system_fault", "detail": str(e)})

    return {"ticket_id": soap_response.IncidentId, "status": "created"}

The agent never knows SOAP exists — it only sees POST /tickets with a JSON schema, exactly like any other tool.

Practical exercise

Case: an agent that manages customer incidents

The agent must: (a) look up customer data in Salesforce (SaaS CRM, REST + OAuth2), (b) create a ticket in a legacy support system that only exposes SOAP, (c) trigger the fulfillment process once the ticket is resolved.

  1. Which protocol/pattern would you use for each of the three integrations, and why?
  2. How do you wrap the legacy SOAP system so it's usable as a tool by the agent?
  3. What OAuth2 scope would you give the Salesforce tool — and what should it NOT be able to do?
See suggested approach

1. Salesforce → synchronous REST (you need the data now to respond). Legacy ticket → synchronous REST too (you need to confirm creation), but wrapped. Fulfillment → asynchronous event (Kafka/EventBridge), doesn't block the conversation.

2. A dedicated adapter service exposes a simple REST endpoint (POST /tickets) that internally translates to the SOAP call — the agent never sees SOAP, only a clean REST contract with its own tool schema.

3. Read-only scope over the authenticated customer's Contact/Case object — never write, and never access to other customers. If a write is needed (e.g., updating a field), that's a separate tool, with its own scope and likely human approval.

Related interview questions
  • How would you expose a legacy SOAP system as a tool for an agent?
  • When would you use an event (Kafka) instead of a direct tool call for an agent action?
  • How do you handle a tool call that needs human approval before executing (e.g., a refund)?
  • Where does the API Gateway fit in an agent's architecture, and why there?
  • How do OAuth2 scopes limit what an agent can do on a user's behalf?
