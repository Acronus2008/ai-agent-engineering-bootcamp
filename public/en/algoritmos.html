Approximate Nearest Neighbor (HNSW) Days 01-02 · RAG
Use
Find the k most semantically similar documents to a query, within an embedding index.
When
Any real-scale RAG — thousands to millions of vectors. With <10k documents, brute-force is enough.
Why
Comparing the query against every vector doesn't scale. HNSW builds a layered graph that lets you jump straight to the right neighborhood.
What it actually means
It trades perfect accuracy (it's approximate) for speed — in RAG, an "almost perfect" top-5 in 10ms beats the exact top-5 in 2s.
Brute-force: O(n·d) per query HNSW: ~O(log n) per query (approximate) HNSW space: O(n·M)
similarity_search.pypython
# Brute-force — correct, but O(n·d). Serves as a baseline / small n.
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def brute_force_top_k(query: np.ndarray, vectors: list[np.ndarray], k: int = 5):
    scored = [(cosine_similarity(query, v), i) for i, v in enumerate(vectors)]
    scored.sort(reverse=True)
    return scored[:k]

# In production you don't reimplement HNSW by hand — you use a library
# (faiss, hnswlib, or the managed vector store). What you do decide
# is the trade-off: higher ef_search = more recall, more latency.
import hnswlib

index = hnswlib.Index(space="cosine", dim=1536)
index.init_index(max_elements=1_000_000, ef_construction=200, M=16)
index.add_items(vectors, ids)
index.set_ef(64)  # ef_search: raise this if recall isn't enough
labels, distances = index.knn_query(query, k=5)
Token Bucket Day 05 · Reliability
Use
Limit throughput toward the LLM provider or a downstream tool.
When
Any outbound traffic that could spike in a loop (from a bug, from prompt injection, or simply legitimate bursts).
Why (vs. sliding window)
Allows short controlled bursts without rejecting legitimate traffic — more flexible than a fixed counter per window.
What it actually means
The "bucket" refills at a constant rate; each request consumes a token. Without tokens, you wait or reject — the mechanism is the full analogy.
Time: O(1) per request Space: O(1) per client
token_bucket.pypython
import time

class TokenBucket:
    def __init__(self, capacity: int, refill_rate_per_s: float):
        self.capacity = capacity
        self.tokens = capacity
        self.refill_rate = refill_rate_per_s
        self.last_check = time.monotonic()

    def allow(self) -> bool:
        now = time.monotonic()
        elapsed = now - self.last_check
        self.last_check = now
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)

        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False  # caller decides: reject, queue, or degrade
Exponential Backoff + Jitter Day 05 · Reliability
Use
Retry a failed call without generating retry storms against an already-degraded system.
When
Any transient failure (timeout, 503) — never for errors that won't change with a retry (e.g. a 400 validation error).
Why
Exponential backoff gives the system time to recover; jitter prevents every client from retrying at the same instant (thundering herd).
What it actually means
Combined with a circuit breaker (Closed → Open → Half-Open), it stops you from keeping at it once it's clear the system is down.
Time: O(1) per attempt Bounded attempts: O(log(delay_max))
backoff.pypython
import random, time

def backoff_delay(attempt: int, base=0.5, cap=20.0) -> float:
    exp = min(cap, base * (2 ** attempt))
    return random.uniform(0, exp)  # "full jitter" — avoids synchronization between clients

def call_with_backoff(fn, max_attempts=4):
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:
            if attempt == max_attempts - 1:
                raise
            time.sleep(backoff_delay(attempt))
Deterministic Hashing (idempotency keys) Days 05, 07 · Reliability / Distributed Systems
Use
Generate a stable key that identifies "this specific operation," to detect duplicates without central coordination.
When
Any write that can be retried — payments, ticket creation, any Saga action.
Why
A hash of the relevant parameters (or a UUID generated once when the flow starts) gives the same key on the same attempt, without needing an external database to "agree" on the key.
What it actually means
At large scale, storing every key seen can be expensive — that's where a Bloom filter comes in: approximate deduplication with controlled false positives and sublinear space.
Hash: O(1) Bloom filter: O(k) per insert/query (k = hash functions) Bloom space: O(m) sublinear vs. storing every key
idempotency.pypython
import hashlib, json

def idempotency_key(operation: str, params: dict) -> str:
    # sort_keys=True: same dict, same hash, regardless of order
    payload = json.dumps({"op": operation, "params": params}, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()

# Approximate deduplication at large scale (millions of keys, bounded memory)
from pybloom_live import BloomFilter

seen = BloomFilter(capacity=10_000_000, error_rate=0.001)

def is_probably_duplicate(key: str) -> bool:
    if key in seen:
        return True  # could be a false positive — verify against the real source before rejecting
    seen.add(key)
    return False
Lamport Timestamps / Vector Clocks Day 07 · Distributed Systems
Use
Determine the causal order of events generated by different services, without relying on synchronized wall clocks.
When
When an order's state is updated from multiple sources (ERP, agent, payment system) and you need to reconcile "what happened first."
Why
Clocks on different machines are never perfectly synchronized — using wall-clock time to order events produces silent inconsistencies.
What it actually means
Each node keeps a counter that increments on every event and syncs (takes the max) when receiving a message — the relative order is determined without a shared clock.
Time: O(n) per event (n = number of nodes, for vector clocks) Simple Lamport: O(1) per event
lamport_clock.pypython
class LamportClock:
    def __init__(self):
        self.time = 0

    def tick(self) -> int:
        self.time += 1  # local event
        return self.time

    def merge(self, received_time: int) -> int:
        # upon receiving a message, the clock "jumps" to the max + 1
        self.time = max(self.time, received_time) + 1
        return self.time
Optimistic Locking (Compare-and-Swap) Day 07 · Distributed Systems
Use
Prevent two concurrent executions (e.g. chat + voice from the same user) from stepping on the same resource at the same time.
When
Critical actions on a shared resource, when conflicts are infrequent (if they're frequent, a pessimistic/distributed lock like Redlock performs better).
Why
It doesn't block anything upfront — it reads the current version, writes only if nobody changed it in the meantime. Cheaper than a real distributed lock when contention is low.
What it actually means
It's the same idea as an HTTP ETag or a WHERE version = ? in SQL — "only update if nobody else touched it since I read it."
Time: O(1) per attempt Retries on conflict: bounded, same as backoff
optimistic_lock.pypython
def update_order_status(order_id: str, new_status: str) -> bool:
    order = db.get(order_id)
    result = db.update(
        order_id,
        {"status": new_status, "version": order.version + 1},
        # condition: only write if the version hasn't changed since the read
        condition="version = :expected_version",
        expected_version=order.version,
    )
    return result.success  # False → someone else won the race, retry with fresh data
Consistent Hashing Day 08 · Cloud Architecture
Use
Distribute sessions or data across nodes (DynamoDB partitions, Agent Runtime instances behind a load balancer).
When
Scaling horizontally by adding or removing nodes, without triggering a massive reshard every time.
Why (vs. hash % n)
With hash(key) % n, changing n remaps almost every key. With a consistent ring, only ~K/n keys get remapped when adding/removing a node.
What it actually means
Nodes and keys sit on the same hash ring; each key belongs to the first node clockwise. "Virtual nodes" prevent a single node from receiving a disproportionate share.
Lookup: O(log n) with a sorted ring (bisect) Space: O(v) with v = virtual nodes
consistent_hash.pypython
import bisect, hashlib

class ConsistentHashRing:
    def __init__(self, nodes: list[str], virtual_nodes: int = 100):
        self.ring: dict[int, str] = {}
        self.sorted_keys: list[int] = []
        for node in nodes:
            for i in range(virtual_nodes):
                h = self._hash(f"{node}#{i}")
                self.ring[h] = node
        self.sorted_keys = sorted(self.ring)

    def _hash(self, key: str) -> int:
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_node(self, key: str) -> str:
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[idx]]
LRU Cache Cross-cutting · Reliability / Cloud
Use
Cache results of expensive tool calls or already-computed embeddings so they aren't recomputed.
When
There's real reuse of queries/results and the cost of recomputing (latency or $/token) is high.
Why
Evicting the least-recently-used entry assumes "what was used recently will be used again soon" — true for most agent traffic patterns.
What it actually means
A hashmap for O(1) lookup + a doubly linked list to know what's "oldest" — move to the front on every access.
Get/Put: O(1) Space: O(capacity)
lru_cache.pypython
from functools import lru_cache

@lru_cache(maxsize=2048)
def embed_text(text: str) -> tuple[float, ...]:
    return tuple(embedding_model.encode(text))  # tuple: hashable, cacheable

# Explicit equivalent, useful when you need TTL or hit-rate metrics:
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.data: OrderedDict = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return None
        self.data.move_to_end(key)  # mark as "just used"
        return self.data[key]

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)  # discard the least recently used
Reservoir Sampling Day 05 · Observability
Use
Sample a representative subset of conversations for human review or LLM-as-judge, without storing 100% of traffic.
When
High volume where persisting/reviewing every trace is too expensive, but you need a statistically valid sample.
Why
You don't know how many elements you'll see in total (it's a stream) — reservoir sampling guarantees every element has an equal probability of ending up in the sample, without knowing n in advance.
What it actually means
As more elements arrive, each new one competes for a spot in the "reservoir" with probability k/i — mathematically this gives a uniform sample without two passes.
Time: O(1) per element Space: O(k) with k = sample size
reservoir_sampling.pypython
import random

class ReservoirSampler:
    def __init__(self, k: int):
        self.k = k
        self.reservoir: list = []
        self.count = 0

    def add(self, item):
        self.count += 1
        if len(self.reservoir) < self.k:
            self.reservoir.append(item)
        else:
            j = random.randint(0, self.count - 1)
            if j < self.k:
                self.reservoir[j] = item  # replace with probability k/count
