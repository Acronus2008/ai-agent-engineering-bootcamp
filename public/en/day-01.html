01

Enterprise AI Fundamentals

What separates an enterprise agent from a chatbot: the building blocks you'll recognize in every architecture from here on.

~90 min Prerequisite: none Connects to: Day 02 — Agent Architecture
Today's objective

By the end of today you should be able to explain, unaided, the 12 base concepts of an enterprise AI system — and above all, translate each one into something you already know from backend, APIs, or cloud. This isn't new content: it's new vocabulary for patterns you've already operated.

Content
01 · LLM

A token-prediction service, not a brain

An LLM receives text (tokens) and predicts, one at a time, the most likely next token — conditioned on everything in its context window. It doesn't "remember" anything between calls: every invocation is independent.

Backend analogyIt's a stateless function: predict(context) → next_token. State (conversation history) is managed by the caller, exactly like a sessionless REST service where the client resends context on every request.
02 · Prompting

The behavior contract

The system prompt defines rules, tone, limits, and format — it's the service configuration. The user prompt is the specific request. A bad system prompt is like a misconfigured service: it works, but unpredictably.

Backend analogySystem prompt ≈ environment variables / config that shape service behavior before real traffic arrives.
03 · Structured Outputs

Forcing the output into a validatable contract

Instead of trusting the model to return parseable free text, you force it (via schema/grammar) to return JSON matching a specific structure.

Backend analogyIt's a DTO with schema validation at the system boundary — same as validating a payload against OpenAPI/JSON Schema before accepting it.
04 · Function / Tool Calling

The model proposes, your backend decides and executes

The LLM never executes code. When it "calls a tool," it actually returns a JSON payload with {name, arguments}. Your backend validates those arguments and decides whether to run the real function. This is the single most important control point in the whole architecture.

Backend analogyLike a webhook the model "fires": the LLM generates the payload, but your code receives, validates, and executes it — with the same authorization rules you'd apply to any untrusted external call.
05 · Agents

A loop: think → act → observe → repeat

An agent is an LLM inside a control loop: it decides on an action (reply or call a tool), executes it (or the system executes it), observes the result, and decides the next step — until it reaches a final answer.

Backend analogyIt's a state machine / event loop with a non-deterministic decision step on each iteration, instead of fixed code-driven transitions.
06 · Agent Orchestration

Coordinating steps, tools, and (sometimes) other agents

Defines how actions are sequenced: a single agent with many tools, or several specialized agents delegating work to each other? It also determines routing, retries, and when to ask for human intervention.

Backend analogyIt's your workflow orchestration layer (think Step Functions or a saga orchestrator), except the "next step" is decided by the model, not a fixed graph.
07 · RAG

Looking up knowledge instead of training it in

Retrieval-Augmented Generation: at answer time, relevant documents are looked up and injected into the prompt. The model doesn't "know" your private data — it queries it in real time, just like an app queries its database.

Backend analogyRAG is a read before responding — like resolving a view with a join/lookup instead of hardcoding the value in code. Fine-tuning, by contrast, would be "baking" the data into the model — expensive and hard to keep current.
08 · Embeddings & Vector DBs

Searching by meaning, not exact match

An embedding turns text into a numeric vector where distance reflects semantic similarity. A vector DB is an index optimized for nearest-neighbor search over those vectors.

Backend analogyLike an inverted index in a full-text search engine, except instead of matching exact tokens, it matches "closeness of meaning" in a high-dimensional space.
09 · Context Window

The memory budget of every request

Everything competes for the same limited space: system prompt, history, documents retrieved by RAG, and tool results. It's measured in tokens and has a ceiling — once full, something gets truncated or dropped.

Backend analogyIt's the heap/memory limit of a per-request process: if you don't manage what goes in, you get the equivalent of an OOM — except here the "crash" is silent quality degradation, not an exception.
10 · Memory

What persists, where, and for how long

Short-term: the current conversation's history, lives in the context. Long-term: facts, preferences, or summaries that persist across sessions, usually in a database external to the model.

Backend analogyShort-term memory ≈ in-memory session state. Long-term memory ≈ persistence in a table/store, with the same usual questions: what gets saved, with what TTL, and who has access.
11 · Hallucinations

The most dangerous failure mode: failing with confidence

The model generates plausible but false text — no exception, no stack trace. In an enterprise context (account balance, order status), this is unacceptable without mitigation.

Backend analogyIt's the equivalent of a service returning 200 OK with incorrect data instead of failing explicitly. That's why every critical factual answer must come from a verifiable tool/RAG result, never from the model's "memory."
12 · Guardrails

Validation middleware around the model

Control layers over input and output: content filters, schema validation, a second model as a "judge," limits on which tools can be called and with what permissions.

Backend analogyIt's your middleware/API gateway layer: sanitizes input, validates output, applies rate limiting and policy — the model is never the only control point.

Implementation example

Tool schema + validation, in code

The skeleton behind the exercise below: the schema the model sees, and the validation that runs before touching the real ERP — never the other way around.

order_agent.pypython
# The schema the model sees — it defines shape, not trust
GET_ORDER_STATUS_SCHEMA = {
    "name": "get_order_status",
    "description": "Looks up an order's status by its ID",
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "pattern": "^[0-9a-fA-F-]{36}$"}
        },
        "required": ["order_id"],
    },
}

def execute_tool_call(name: str, args: dict) -> dict:
    # 1. Validate BEFORE touching the real system — never trust
    #    only the schema the model "saw".
    if name == "get_order_status":
        order_id = args.get("order_id", "")
        if not UUID_PATTERN.match(order_id):
            # Structured error, not a raw exception —
            # the agent receives it as an observation and can react.
            return {"error": "invalid_order_id", "detail": "expected UUID format"}

        try:
            status = erp_client.get_status(order_id)  # single source of truth
            return {"status": status}
        except ERPTimeoutError:
            return {"error": "upstream_timeout"}

    return {"error": "unknown_tool"}

Notice what this code doesn't do: it never lets the agent assert a status without going through erp_client.get_status — that's Day 01's anti-hallucination barrier turned into code.

Practical exercise

Case: order status agent

A company wants an agent that answers "where's my order?" by querying the internal ERP. Design the function calling flow by answering:

  1. What does the schema for the get_order_status tool look like? Which parameters are required?
  2. The LLM calls the tool with order_id: "ABC", but the real system expects a numeric UUID. What happens?
  3. How do you keep the model from hallucinating an order_id or inventing a shipping status if the tool fails?
See suggested approach

1. Schema: {order_id: string, required, pattern: UUID} — describe the schema in the tool definition so the model knows the expected format, but never trust that alone.

2. Validation: your backend validates order_id before touching the ERP. If it doesn't match the pattern, return a structured error to the tool (not a raw exception) — the agent receives it as an observation and can ask the user for clarification or retry with the correct format.

3. Anti-hallucination: the agent's prompt must state explicitly that it can only assert an order status if it comes from a successful tool result — never "remembered" or "inferred." If the tool fails, the correct response is to admit the lookup failed, not invent a plausible status.

Related interview questions
  • When would you choose RAG over fine-tuning, and vice versa?
  • Who decides whether a tool executes: the model or your system? Why does that distinction matter?
  • What happens when a tool call fails mid-way through an agent flow?
  • How do you reduce the hallucination rate in an agent that provides sensitive factual information?
  • Why is context window size also a cost and latency decision, not just a capacity one?
