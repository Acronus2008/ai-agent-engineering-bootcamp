03

Enterprise Integration

El agente vive rodeado de CRM, ERP, colas y APIs legacy. Hoy es puro mapeo: qué protocolo usar para qué capacidad, y cómo autorizar cada llamada.

~90 min Prerrequisito: Día 02 Conecta con: Día 04 — Security
Objetivo del día

Ya sabes construir APIs, consumir eventos y manejar OAuth2 — eso no cambia. Lo que cambia es quién decide cuándo llamar cada integración: hoy es un LLM, no una rama de código fija, así que cada integración necesita un contrato más explícito y más defensivo.

Principio clave
"El agente no debería acceder directamente a los sistemas críticos; debe hacerlo mediante herramientas y APIs con autorización y controles adecuados."
Contenido
REST

El default para exponer una tool

Request/response síncrono, contrato predecible, fácil de describir como schema para el LLM. Es la forma más simple de envolver una capacidad de negocio como tool.

GraphQL

Potente para el humano, ambiguo para el modelo

Resuelve over/under-fetching, pero un schema GraphQL completo es difícil de acotar como definición de tool (demasiadas combinaciones posibles). En la práctica: envuelve el GraphQL detrás de una tool REST-like con queries predefinidas y parametrizadas.

Kafka / Event-driven

Para acciones que no necesitan respuesta inmediata

Si la acción del agente dispara un proceso downstream (fulfillment, notificación a otro equipo) y no necesita esperar el resultado para continuar la conversación, un evento es mejor que una llamada síncrona: desacopla al agente de la disponibilidad de ese sistema.

Webhooks

La forma en que el mundo despierta al agente

Cuando algo pasa fuera del turno de conversación (un pago se confirma, un humano aprueba una acción pendiente), un webhook reactiva el agente para continuar donde quedó — clave para flujos con human-in-the-loop.

Databases

Nunca una tool en sí misma

El agente no debería tener una tool tipo "run SQL query". Siempre pasa por un servicio que valida, aplica reglas de negocio y deja rastro de auditoría — igual que exigirías en cualquier sistema con usuarios externos.

CRM / ERP / SaaS / Legacy

La realidad: rara vez hay una API limpia

Muchas veces necesitas un adapter/anti-corruption layer entre el sistema legacy y la tool que expones al agente — traduce el modelo de datos viejo a un contrato simple y estable.

OAuth2 / OIDC

Quién autoriza qué, en nombre de quién

El agente actúa en nombre de un usuario (delegated authorization) o con un service account de scope acotado. El token que usa la tool debe llevar los mismos scopes que tendría el usuario si hiciera la acción manualmente — nunca más.

IAM

Least privilege, por tool

Cada tool tiene su propio scope mínimo necesario. Una tool de "consultar pedido" no debería poder "cancelar pedido" — aunque ambas toquen el mismo sistema.

API Gateway

El chokepoint donde vive el control

Todas las tool calls del agente pasan por un punto central de auth, rate limiting y logging — es también donde suele vivir buena parte de los guardrails de seguridad (Día 04).

Diagrama de implementación

La capa de integración completa

Cómo se ve en la práctica el principio del día: el agente solo habla con el API Gateway, nunca directo con CRM, legacy o el bus de eventos.

Ejemplo de implementación

El adapter que envuelve el sistema SOAP legacy

La tool que ve el agente es REST limpio; el adapter absorbe toda la fealdad de SOAP detrás.

ticket_adapter.pypython
from fastapi import FastAPI, HTTPException
import zeep  # cliente SOAP

app = FastAPI()
soap_client = zeep.Client("https://legacy.internal/tickets?wsdl")

# Contrato REST limpio — esto es lo único que el agente conoce como tool
@app.post("/tickets")
def create_ticket(payload: TicketCreate, token: str = Depends(verify_oauth_scope)):
    if not token.has_scope("tickets:write"):
        raise HTTPException(403, "missing tickets:write scope")

    try:
        # Traduce el modelo REST simple al request SOAP real
        soap_response = soap_client.service.CreateIncident(
            CustomerId=payload.customer_id,
            Description=payload.description,
            Priority=map_priority(payload.priority),
        )
    except zeep.exceptions.Fault as e:
        # Error estructurado — el agente lo ve como observación, no como crash
        raise HTTPException(502, {"error": "legacy_system_fault", "detail": str(e)})

    return {"ticket_id": soap_response.IncidentId, "status": "created"}

El agente nunca sabe que existe SOAP — solo ve POST /tickets con un schema JSON, exactamente como cualquier otra tool.

Ejercicio práctico

Caso: agente que gestiona incidencias de un cliente

El agente debe: (a) consultar datos del cliente en Salesforce (CRM SaaS, REST + OAuth2), (b) crear un ticket en un sistema legacy de soporte que solo expone SOAP, (c) disparar el proceso de fulfillment cuando el ticket se resuelve.

  1. ¿Qué protocolo/patrón usarías para cada una de las tres integraciones, y por qué?
  2. ¿Cómo envuelves el sistema legacy SOAP para que sea una tool utilizable por el agente?
  3. ¿Qué scope de OAuth2 le darías a la tool de Salesforce — y qué NO debería poder hacer?
Ver enfoque sugerido

1. Salesforce → REST síncrono (necesitas el dato ya para responder). Ticket legacy → REST síncrono también (necesitas confirmar creación), pero envuelto. Fulfillment → evento asíncrono (Kafka/EventBridge), no bloquea la conversación.

2. Un servicio adapter propio expone un endpoint REST simple (POST /tickets) que internamente traduce a la llamada SOAP — el agente nunca ve SOAP, solo ve un contrato REST limpio con su propio schema de tool.

3. Scope de solo lectura sobre el objeto Contact/Case del cliente autenticado — nunca write, y nunca acceso a otros clientes. Si se necesita escribir (ej. actualizar un campo), es una tool distinta, con su propio scope y probablemente aprobación humana.
