Production AI & Reliability

Retries, circuit breakers e idempotency ya los dominas de backend clásico. Hoy: aplicarlos al loop de un agente, y la capa nueva — evals, costo por token y versionado de prompts.

~100 min Prerrequisito: Día 04 Conecta con: Día 06 — System Design
Objetivo del día

Cerrar la Semana 1 con la pregunta que separa un demo de una solución real: ¿qué pasa cuando algo falla? — un tool call, el LLM, la red — y cómo lo sabrías antes de que te lo diga un cliente enojado.

Contenido
Reliability clásica, aplicada al loop del agente
Retries & Timeouts

Todo tool call y toda llamada al LLM necesita ambos

Sin timeout, el loop del agente puede quedar colgado indefinidamente a mitad de una conversación. Los retries deben ser acotados (backoff, máximo de intentos) — nunca dejar que el agente reintente indefinidamente dentro de su propio razonamiento.

Circuit Breakers

Fallar rápido cuando una dependencia está caída

Si una tool falla repetidamente, el circuit breaker corta las llamadas y fuerza un fallback inmediato — evita que el agente siga "intentando" mientras el usuario espera.

Idempotency

Crítico cuando el que reintenta puede ser el agente O el usuario

Un timeout seguido de un retry, o un usuario repitiendo "hazlo de nuevo", puede disparar la misma acción dos veces. Cada tool que modifica estado necesita una idempotency key.

Fallbacks

Una respuesta degradada es mejor que colgarse

Si una tool no está disponible: "no puedo consultar eso ahora, te conecto con una persona" — nunca dejar que el agente invente el dato faltante.

Rate Limiting

Protege al proveedor del LLM y a los sistemas downstream

Un agente en loop (por bug o por injection) puede generar tráfico explosivo hacia tools o hacia el proveedor del modelo — necesita límites igual que cualquier cliente automatizado.

Queues & DLQ

Para las acciones asíncronas que dispara el agente

Un evento de fulfillment que falla tras sus reintentos no debe perderse silenciosamente — va a una dead-letter queue para investigación, igual que en cualquier pipeline async.

Observability, Tracing, Metrics, Logging

Un solo trace que cruza LLM calls + tool calls + orquestación

La diferencia con backend clásico: necesitas ver la cadena de razonamiento completa de un request — qué decidió el modelo, qué tool llamó, con qué resultado, en qué orden — como un único trace distribuido, no llamadas sueltas.

Lo específico de AI en producción
Model Fallback

Qué pasa si el proveedor del LLM está caído

Arquitectura pluggable: si el modelo primario falla o degrada, se cae a un modelo secundario (otro proveedor o uno más simple) — con la expectativa explícita de que la calidad puede bajar temporalmente.

Token Usage & Costo

Un loop descontrolado también es un incidente de costo

Cada sesión/request debería tener un presupuesto de tokens. Sin límite, un bug en la lógica de orquestación (o una injection) puede generar un loop que dispara el costo sin que nadie lo note hasta la factura.

Latency

El LLM es casi siempre el paso más lento del pipeline

Streaming de respuesta, paralelizar tool calls independientes cuando sea posible, y presupuestar latencia por paso — igual que optimizarías cualquier request de alta latencia.

Hallucination Monitoring

No es un test que pasas una vez, es una métrica continua

Señales en producción: tasa de respuestas sin soporte en los documentos recuperados, contradicciones detectadas por un modelo evaluador, feedback negativo de usuarios — trackeadas en el tiempo, no solo validadas pre-lanzamiento.

Tool Failures

Deben llegar al agente como observación estructurada, no tragarse

Si una tool falla y el error se traga silenciosamente, el agente puede alucinar un resultado. El error estructurado le da al agente la información para decidir: reintentar, usar un fallback, o escalar.

Prompt / Version Management

Los prompts son código: versionados, testeados, con rollback

Un cambio de prompt es un cambio de comportamiento en producción — mismo rigor que un deploy: canary, evaluación antes de 100% rollout, capacidad de revertir.

Agent Evaluation

Offline (golden set) + online (muestreo de conversaciones reales)

Un set de casos de prueba fijos detecta regresiones antes de deploy. Un muestreo continuo de conversaciones reales (revisión humana o LLM-as-judge) detecta lo que el golden set no anticipó.

Diagrama de implementación

Retry + idempotency en acción

El mismo idempotency_key viaja en ambos intentos — es lo que convierte un timeout más un retry en "una sola operación", no en dos.

Ejemplo de implementación

Wrapper idempotente con retry acotado

La key se genera una sola vez, al iniciar el flujo — nunca dentro del loop de retry.

reliable_tool_call.pypython
import time, uuid

def call_with_retry(fn, *, max_attempts=2, timeout_s=5, backoff_s=1):
    idempotency_key = str(uuid.uuid4())  # generada UNA vez, fuera del loop

    for attempt in range(1, max_attempts + 1):
        if circuit_breaker.is_open(fn.__name__):
            return fallback_response()  # fail fast, no más intentos

        try:
            result = fn(idempotency_key=idempotency_key, timeout=timeout_s)
            circuit_breaker.record_success(fn.__name__)
            return result
        except TimeoutError:
            circuit_breaker.record_failure(fn.__name__)
            if attempt == max_attempts:
                return fallback_response()
            time.sleep(backoff_s * attempt)  # backoff corto, acotado

def fallback_response() -> dict:
    # Honesto con el usuario, nunca inventa un resultado
    return {"status": "pending_verification", "message": "Estamos confirmando tu ticket."}

El circuit_breaker es solo un contador con umbral y un flag — no necesitas una librería para empezar, solo la disciplina de nunca reintentar sin límite.

Ejercicio práctico

Caso: la tool "crear ticket" falla intermitentemente por timeout

Uno de cada veinte llamados a create_ticket hace timeout a los 5s, pero el ticket a veces sí se crea del lado del sistema legacy (el timeout es en la respuesta, no en la operación).

  1. ¿Cómo diseñas la idempotency key para esta tool?
  2. ¿Qué política de retry aplicarías, y por qué?
  3. ¿Qué ve el usuario mientras tanto, y qué queda en el trace para depurarlo después?
Ver enfoque sugerido

1. Una idempotency key generada por el agente al iniciar la operación (no por el sistema legacy), enviada en cada intento — el backend del ticket la usa para detectar "ya procesé esto" y devolver el mismo resultado en vez de crear un duplicado.

2. Retry único con backoff corto, y si vuelve a fallar, no seguir reintentando indefinidamente — pasar a fallback (avisar al usuario que se está verificando) en vez de que el agente "decida" reintentar por su cuenta dentro del razonamiento.

3. El usuario ve un mensaje honesto ("estoy confirmando si se creó el ticket"), nunca una afirmación no verificada. El trace debe registrar la idempotency key, cada intento, su timeout, y el resultado final de la verificación — para poder reconstruir exactamente qué pasó si el cliente reclama un ticket duplicado.
