Distributed Systems

CAP, Saga, Outbox, idempotency — todo esto ya lo conoces. Hoy: aplicarlo a la pregunta que todo entrevistador de FDE hace tarde o temprano.

~100 min Prerrequisito: Día 06 Conecta con: Día 08 — Cloud Architecture
Objetivo del día

Responder con solidez: "¿qué ocurre si un agente intenta ejecutar dos veces la misma operación?" — y hacerlo cubriendo idempotency, límites transaccionales, autorización, auditoría y estrategia de retry en una sola respuesta estructurada.

Contenido
CAP Theorem

Aplicado a decisiones de tool, no solo de base de datos

Durante una partición, ¿la tool prioriza consistencia (rechaza el request) o disponibilidad (responde con datos potencialmente desactualizados)? Depende del costo de cada error: un "estado de pedido" desactualizado es tolerable; un "saldo disponible" no.

Eventual Consistency

Aceptable para la mayoría de las lecturas de un agente

Si el agente lee de un read replica o de un índice de RAG que se actualiza cada X minutos, eso es eventual consistency — perfectamente válido para preguntas informativas, no para decisiones que muevan dinero o inventario.

Distributed Transactions & Saga

Una acción del agente casi nunca es una sola transacción ACID

"Procesar un reembolso" puede tocar: sistema de pagos, base de pedidos, sistema de notificaciones — cada uno con su propia transacción local. El patrón Saga encadena estos pasos con compensating actions: si el paso 3 falla, deshaces (o compensas) los efectos de los pasos 1 y 2 ya ejecutados.

Outbox Pattern

Publicar un evento de forma confiable junto a un cambio de estado

Cuando una tool actualiza su base de datos Y necesita emitir un evento (ej. "reembolso procesado" → notificar al agente para que informe al usuario), escribir ambos en la misma transacción local (tabla de outbox) y publicar el evento después, de forma asíncrona, evita el caso donde el estado cambia pero el evento se pierde.

Ordering

El orden de las tool calls importa, y no siempre lo garantiza el modelo

Si el agente debe "verificar inventario" antes de "cobrar", esa precondición debe validarse dentro de la tool misma (rechazar el cobro si no hay verificación previa registrada) — nunca confiar en que el LLM siempre respetará el orden correcto.

Exactly-once vs At-least-once

Exactly-once no existe a nivel de red — se simula con idempotency

Asume que cada tool call puede llegar más de una vez (at-least-once, por retries). El resultado "effectively-once" se logra combinando entrega at-least-once con una tool idempotente — no persiguiendo exactly-once real, que es prácticamente imposible de garantizar end-to-end.

Distributed Locks

Cuando dos canales pueden disparar la misma acción a la vez

Si el mismo usuario interactúa por chat y por voz simultáneamente, un lock sobre la clave de la operación (ej. order_id) evita que ambas conversaciones ejecuten la misma acción crítica en paralelo.

Backpressure, Queues & Streams

Repaso rápido con el vocabulario de agentes

Backpressure = el sistema le dice al orquestador "más despacio" en vez de caerse. Queues = distribución punto a punto de trabajo (una tarea, un consumidor). Streams (Kafka) = log ordenado, múltiples consumidores independientes — útil cuando varios sistemas necesitan reaccionar al mismo evento del agente.

Diagrama de implementación

El Saga de reembolso, paso a paso

Cuatro pasos con su propia transacción local — y una rama explícita para cuando el paso 3 falla después de que el pago (paso 2) ya se emitió.

Ejemplo de implementación

Orquestador de Saga, en código

El patrón general: cada paso sabe cómo ejecutarse y, si aplica, cómo compensarse.

refund_saga.pypython
class SagaStep:
    def __init__(self, name, execute, compensate=None):
        self.name, self.execute, self.compensate = name, execute, compensate

def run_saga(steps: list[SagaStep], context: dict):
    completed = []
    for step in steps:
        try:
            context = step.execute(context)
            completed.append(step)
        except StepFailed as e:
            # Compensa en orden inverso — pero el pago (paso 2) no se
            # "revierte": su compensación real es escalar, no deshacer.
            for done in reversed(completed):
                if done.compensate:
                    done.compensate(context)
            raise

refund_saga = [

]

Ejercicio práctico

Caso: procesar un reembolso vía agente

Flujo: (1) verificar elegibilidad (lectura), (2) emitir el reembolso en el proveedor de pagos (escritura externa, puede fallar parcialmente), (3) actualizar el estado del pedido (escritura interna), (4) notificar al cliente.

  1. ¿Cómo estructuras esto como Saga? ¿Cuál es la compensating action si el paso 3 falla después de que el paso 2 ya se ejecutó?
  2. ¿Dónde usarías el Outbox pattern?
  3. ¿Qué necesita ser idempotente, y con qué key?
Ver enfoque sugerido

1. Cada paso es una transacción local con su propia compensación. Si el paso 3 (actualizar pedido) falla después de que el reembolso ya se emitió (paso 2), la compensación NO es "revertir el reembolso" (rara vez es posible ni deseable) — es reintentar el paso 3 hasta lograrlo, o escalar a revisión humana si sigue fallando, dejando el reembolso ya emitido registrado como "pendiente de reconciliar".

2. En el paso 3: al actualizar el estado del pedido en la misma transacción local, se escribe también el evento "reembolso procesado" en una tabla outbox — un proceso separado lo publica de forma confiable, disparando la notificación al cliente (paso 4) sin acoplar esa notificación a la transacción de la base de datos.

3. La llamada al proveedor de pagos (paso 2) necesita una idempotency key generada al iniciar el flujo (no en cada retry) — así, si el agente reintenta todo el flujo por un timeout, el proveedor de pagos reconoce la misma operación y no emite un segundo reembolso.
