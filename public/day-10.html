Todo lo de la Semana 2, en un solo caso, bajo tiempo. Esta es la simulación más cercana a la entrevista técnica real.

El caso
Enunciado

"Una empresa quiere implementar un agente de IA que atienda clientes por voz, consulte sistemas internos, ejecute operaciones y transfiera la conversación a un humano cuando sea necesario."

⏱ 60 min para resolver 🎙 Ideal: grabarte hablando, no solo escribir 📋 Usa el framework de 16 pasos del Día 06
Instrucciones

No leas la solución todavía. Pon un timer de 60 minutos y recorre los 16 pasos del Día 06 en voz alta, como si el entrevistador estuviera frente a ti. Dibuja el diagrama en papel. Solo después de terminar (o de que se acabe el tiempo), compara con el enfoque sugerido abajo.

Enfoque sugerido
Ver la solución completa (los 16 pasos)
  1. 1. Clarificar "¿Qué tipo de operaciones ejecuta — solo consultas, o también acciones que modifican estado (ej. cancelar un servicio)? ¿Qué canal de voz — call center tradicional o WhatsApp/app?" Asumimos: call center entrante, consultas + acciones de bajo-medio riesgo, con reembolsos/cambios de alto impacto escalando a humano.
  2. 2. Usuarios Clientes finales (llaman por teléfono), agentes humanos de soporte (reciben el handoff), supervisores (auditan calidad de las llamadas).
  3. 3. Objetivos Reducir tiempo de espera y costo por llamada, manteniendo NPS y una tasa de escalamiento a humano <20% (patrón de Product Thinking del Día 19 del plan).
  4. 4. Funcionales Autenticar al llamante, consultar cuenta/pedidos, ejecutar acciones simples (reprogramar, actualizar dato), transferir con contexto a un humano.
  5. 5. No funcionales Latencia de respuesta <1.5s percibida (crítico en voz — silencios largos se sienten como falla), alta disponibilidad 24/7, picos de tráfico en horario comercial.
  6. 6. Restricciones Sistemas legacy de CRM, regulación de grabación de llamadas, el equipo de soporte humano ya opera con un dialer existente.
  7. 7. Arquitectura de alto nivel Teléfono → STT → Agent Runtime → (Tools/RAG) → TTS → Teléfono, con handoff a un humano vía el dialer existente.
  8. 8. Arquitectura del agente El diagrama base del Día 02: Agent Runtime + LLM + Memory (estado de la llamada) + RAG (FAQ/políticas) + Tools (CRM, sistema de reprogramación).
  9. 9. Integraciones CRM vía REST + OAuth2 (Día 03), acciones que modifican estado con idempotency key, transferencia de llamada vía API del proveedor de telefonía.
  10. 10. Datos Estado de la llamada en DynamoDB (Día 08), historial de cliente vía RAG sobre la base de conocimiento, nunca persistir el audio crudo más de lo estrictamente necesario por compliance.
  11. 11. Seguridad Autenticación por voz es más débil que en chat (sin UI visual) — PIN verbal o verificación de 2 factores antes de cualquier acción sensible. Tools de solo lectura sin restricción; tools de escritura con scope mínimo (Día 04).
  12. 12. Resiliencia Si el STT falla o hay ruido excesivo, fallback a "no te escuché bien, ¿puedes repetir?" antes de escalar. Si el LLM está lento, un mensaje de espera evita silencio incómodo (percibido como falla en voz).
  13. 13. Observabilidad Trace por llamada completo (Día 05): transcript, tool calls, decisión de escalar o no, y tiempo en cada etapa del pipeline STT→LLM→TTS.
  14. 14. Escalabilidad El cuello de botella más probable es el proveedor de STT/TTS bajo picos de tráfico — diseñar con múltiples proveedores o colas de espera con estimación de tiempo, no caída del servicio.
  15. 15. Trade-offs Un modelo más grande da mejores respuestas pero más latencia — en voz, la latencia percibida pesa más que en chat, así que se prioriza un modelo más rápido con RAG bien acotado sobre uno más "inteligente" pero lento.
  16. 16. Rollout Piloto con un subconjunto de tipos de llamada de bajo riesgo (consultas de estado), medir tasa de resolución y NPS antes de habilitar acciones que modifican estado.
Consideraciones específicas de voz
Lo que cambia frente a un canal de chatLatencia percibida (un silencio de 2s se siente como falla, un delay de 2s en chat no), manejo de interrupciones (barge-in: el usuario habla mientras el agente responde), y autenticación sin UI visual. Ejemplo de implementación

Manejo de barge-in, en código

El caso específico de voz que no existe en chat: cancelar el audio que se está reproduciendo en cuanto el usuario empieza a hablar encima.

voice_session.pypython
class VoiceSession:
    def __init__(self, call_id: str):
        self.call_id = call_id
        self.tts_task: asyncio.Task | None = None

    async def on_audio_chunk(self, chunk: bytes):
        # Si el agente está hablando y llega audio nuevo del usuario,
        # es barge-in: corta la reproducción YA, no esperes a que termine.
        if self.tts_task and not self.tts_task.done():
            self.tts_task.cancel()
            await self.telephony.stop_playback(self.call_id)

        await self.stt_stream.feed(chunk)

    async def on_utterance_end(self, transcript: str):
        response_text = await self.agent_runtime.handle_message(self.call_id, transcript)
        self.tts_task = asyncio.create_task(self._speak(response_text))

    async def _speak(self, text: str):
        audio_stream = await self.tts.synthesize(text)
        await self.telephony.play(self.call_id, audio_stream)

La cancelación explícita del tts_task es lo que evita que el agente "siga hablando" sobre el usuario — el error de UX más notorio en agentes de voz mal implementados.
