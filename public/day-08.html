Cloud Architecture (AWS)

Ya conoces los servicios. Hoy el objetivo es defender la elección, no listar características — practicando las cinco comparaciones que más aparecen en entrevista.

~90 min Prerrequisito: Día 07 Conecta con: Día 09 — Composition Case
Objetivo del día

El objetivo no es memorizar servicios — es justificar decisiones y trade-offs. Recorre las cinco comparaciones aplicadas al mismo caso: un agente de soporte que necesita ejecutar tools, orquestar un flujo con pasos, y guardar estado de conversación.

Las cinco comparaciones
Lambda vs ECS / EKS
LambdaEjecución de tools individuales: corta duración, stateless, tráfico impredecible. Pagas por invocación, cold start aceptable si la tool no es latency-crítica.
ECS / EKSEl Agent Runtime en sí: proceso de larga duración, mantiene conexiones (streaming al usuario), necesita warm start garantizado y más control sobre recursos.
API Gateway vs ALB
API GatewayLa capa de tool calls del agente: auth por ruta, throttling, validación de request/schema por endpoint — encaja con muchos endpoints pequeños y bien definidos (una tool = una ruta).
ALBRouting a un número menor de servicios/contenedores de larga duración, más barato a alto throughput, menos "inteligencia" por request.
SQS vs Kafka (MSK)
SQSDistribución de trabajo punto a punto: una cola de "acciones pendientes de aprobación humana", un solo consumidor procesa cada mensaje una vez.
Kafka / MSKUn evento del agente ("conversación completada") que varios sistemas independientes necesitan consumir (analytics, CRM sync, billing) — cada consumidor mantiene su propio offset.
Step Functions vs Kafka
Step FunctionsOrquestar una secuencia definida con retry y manejo de error built-in — el ajuste natural para implementar la Saga del Día 07 (reembolso: verificar → cobrar → actualizar → notificar).
KafkaReacciones desacopladas donde nadie necesita "poseer" la secuencia completa — cada sistema reacciona al evento a su propio ritmo, sin un orquestador central.
DynamoDB vs RDS / PostgreSQL
DynamoDBEstado de conversación: patrón de acceso por clave (session_id), necesita escalar con conversaciones concurrentes, lecturas de baja latencia, poca necesidad de joins.
RDS / PostgreSQLDatos de negocio relacionales (pedidos, clientes) donde necesitas joins, consistencia fuerte y queries complejas — no el lugar para el historial de chat.
El resto del stack, en una línea cada uno
EventBridge

Bus de eventos con schema, para rutear eventos del agente a múltiples targets según reglas — sin construir tu propio router.

S3

Donde aterrizan los documentos crudos antes de que el pipeline de ingesta de RAG (Día 02) los chunkee y embeba.

Secrets Manager

Las tools nunca tienen credenciales en código o env vars planas — las obtienen en runtime, con rotación automática.

CloudWatch (+ X-Ray)

El punto de agregación de logs/métricas, y la forma AWS-nativa de construir el trace distribuido del Día 05.

IAM

Cada Lambda de tool tiene su propio role con el permiso mínimo — la versión concreta del least privilege del Día 04.

Ejemplo de implementación

Disparar el Saga desde el Agent Runtime

El ECS Runtime no ejecuta el Saga directamente — dispara una ejecución de Step Functions y sigue con la conversación.

trigger_refund_saga.pypython
import boto3, json, uuid

sfn = boto3.client("stepfunctions")

def start_refund_saga(order_id: str, amount: float) -> str:
    execution_name = f"refund-{order_id}-{uuid.uuid4().hex[:8]}"

    response = sfn.start_execution(
        stateMachineArn=REFUND_SAGA_ARN,
        name=execution_name,        # Step Functions rechaza nombres duplicados
        input=json.dumps({                  # → idempotency gratis a nivel de ejecución
            "order_id": order_id,
            "amount": amount,
            "idempotency_key": execution_name,
        }),
    )
    return response["executionArn"]  # el agente puede consultar el estado luego

El nombre de la ejecución hace doble función: identifica el run y actúa como idempotency key — Step Functions rechaza un start_execution con un nombre ya usado.

Ejercicio práctico

Caso: llevar el agente de soporte (Día 02) a AWS

Decide, con justificación de una frase cada una:

  1. ¿Dónde vive el Agent Runtime — Lambda o ECS?
  2. ¿Dónde vive el estado de la conversación?
  3. ¿Cómo implementas el Saga de "procesar reembolso" del Día 07 con servicios AWS concretos?
Ver enfoque sugerido

1. ECS (o similar), porque el runtime necesita mantener el streaming de la respuesta al usuario y hacer múltiples llamadas al LLM/tools dentro del mismo request — un cold start de Lambda en cada turno de conversación sería una mala experiencia. Las tools individuales sí pueden ser Lambdas.

2. DynamoDB, indexado por session_id — acceso de baja latencia por clave, y escala naturalmente con conversaciones concurrentes sin necesidad de joins.

3. Step Functions orquesta los 4 pasos (verificar → cobrar → actualizar pedido en RDS → notificar), con retry configurado por paso y una rama de error explícita hacia una cola SQS de "revisión humana" si el paso de actualización falla después de que el cobro ya se emitió.
