Arquitectura de AI Agents

Los mismos 12 conceptos de ayer, ahora como cajas en un diagrama: dónde vive cada componente y cómo se conecta con los sistemas de la empresa.

Objetivo del día

Pasar de "sé qué es RAG" a "sé dónde dibujar la caja de RAG en un diagrama de arquitectura, y qué hay a cada lado". Al terminar deberías poder dibujar de memoria el diagrama base de un agente enterprise.

Diagrama base
Contenido
Agent Runtime

El loop que orquesta todo lo demás

Es el proceso que recibe el mensaje del usuario, arma el contexto (system prompt + memory + resultados de RAG), llama al LLM, interpreta su decisión, ejecuta tools si corresponde, y repite hasta tener una respuesta final.

Analogía backendEs tu application server orquestando una transacción de negocio que toca varios sistemas — salvo que el "controlador" de cada paso es una decisión del modelo, no una rama de código fija.
Tools

La única puerta hacia los sistemas reales

Cada capacidad de negocio (consultar CRM, crear un ticket, actualizar un pedido) se expone como una tool con schema de entrada/salida y su propio scope de autorización. El agente ve una lista de tools disponibles — nunca credenciales ni acceso directo.

Analogía backendEs exactamente un Backend-for-Frontend: envuelve sistemas legacy/internos detrás de un contrato limpio, con autorización por endpoint.
Memory (en arquitectura)

Dos tiers, dos lugares físicos distintos

Short-term vive en el contexto de la sesión activa (cache/proceso). Long-term vive en un store persistente (DB relacional, documento o vector store) y se recupera explícitamente al iniciar una sesión nueva.

Analogía backendShort-term ≈ session cache (Redis). Long-term ≈ tabla de perfil/historial que consultas al autenticar al usuario.
RAG (en arquitectura)

Dos pipelines separados: ingesta y consulta

Ingesta (offline/batch): documentos → chunking → embeddings → vector store. Consulta (online, por request): pregunta → embedding → búsqueda por similitud → inyección en el prompt.

Analogía backendIngesta ≈ tu pipeline ETL que alimenta un índice de búsqueda. Consulta ≈ el query en caliente contra ese índice en cada request — misma separación read/write que ya conoces.
State

Qué se está ejecutando, y en qué paso

Incluye: historial de la conversación, qué tools se llamaron y con qué resultado, y si hay una acción pendiente de aprobación humana. Es lo que necesitas persistir para poder pausar y reanudar un flujo largo.

Analogía backendEs el execution history de un workflow engine (piensa Step Functions): cada paso, su input, su output, y el puntero de "dónde estamos ahora".
Agent Orchestration

Single-agent vs multi-agent

Un single agent con varias tools es más simple de operar y depurar. Un multi-agent (ej. planner + specialists) tiene sentido cuando necesitas separar dominios de conocimiento, límites de seguridad distintos por tool-set, o paralelismo real entre subtareas.

CriterioSingle-agentMulti-agent
Complejidad operativaBajaAlta (routing, handoffs, debugging distribuido)
Aislamiento de seguridadUn solo scope de toolsScopes distintos por agente/dominio
Cuándo convieneDominio acotado, pocas toolsDominios heterogéneos, necesidad de especialización
Riesgo típicoPrompt sobrecargadoCoordinación frágil entre agentes
Ejemplo de implementación

El loop del Agent Runtime, en código

El esqueleto real detrás de las cajas del diagrama: arma contexto, llama al modelo, ejecuta tools, repite hasta tener respuesta final.

agent_runtime.pypython
class AgentRuntime:
    def __init__(self, llm_client, tools: dict, memory_store, rag_index):
        self.llm = llm_client
        self.tools = tools            # {nombre: función ejecutable}
        self.memory = memory_store    # short-term + long-term
        self.rag = rag_index

    def handle_message(self, session_id: str, user_message: str) -> str:
        history = self.memory.get_conversation(session_id)
        relevant_docs = self.rag.search(user_message, top_k=3)
        context = build_context(history, relevant_docs)

        while True:  # el loop: pensar → actuar → observar
            response = self.llm.call(context, tools=self.tools_schema())

            if response.stop_reason == "tool_use":
                tool_fn = self.tools.get(response.tool_name)
                result = tool_fn(**response.tool_args)  # validado dentro de tool_fn
                context.append_tool_result(response.tool_name, result)
                continue  # vuelve a llamar al LLM con el resultado

            # stop_reason == "end_turn" → respuesta final
            self.memory.save_turn(session_id, user_message, response.text)
            return response.text

El while True es el mecanismo real detrás de "el agente decide el siguiente paso" — no hay nada más místico que un loop con una condición de salida clara.

Ejercicio práctico

Caso: agente de soporte al cliente

Debe: (a) responder preguntas frecuentes con RAG, (b) consultar estado de pedidos en el ERP, (c) escalar a un humano cuando no tenga certeza. Dibuja las cajas del diagrama para este caso y responde:

  1. ¿Este caso justifica multi-agent, o un single agent con 2 tools + RAG es suficiente? ¿Por qué?
  2. ¿Dónde está el límite de confianza — qué puede decidir el agente solo y qué requiere aprobación humana?
  3. ¿Qué pasa con el state si la conversación se corta a mitad de una consulta al ERP?
Ver enfoque sugerido

1. Single agent alcanza: son dos dominios relacionados (soporte) y pocas tools. Multi-agent aquí sería sobre-ingeniería — añade coordinación sin beneficio real.

2. El agente puede responder FAQ y consultar estado libremente (son operaciones de solo lectura). Cualquier acción que modifique estado del pedido (cancelar, reembolsar) debería requerir handoff a humano o approval workflow explícito — no autonomía directa.

3. El state debe persistir el resultado parcial de la tool call (o su ausencia) para que, al reanudar, el agente sepa si ya consultó el ERP o debe reintentar — evita duplicar la consulta o perder el contexto de la conversación.
